# Solver parity corpus & generated OpenAPI client (issue #39)

This note documents how this app consumes the two contracts published by the
[`color_matching`](https://github.com/viamin/color_matching) server:

1. the **OpenAPI document** (`/api/v1/openapi.json`, viamin/color_matching#110) — the source for the generated typed API client, and
2. the **solver parity corpus** (`priv/parity/v1/corpus.json`, viamin/color_matching#111) — golden vectors that keep `WeightedSquaredErrorScorer` in lockstep with the server's `ColorMatching.WeightedSquaredError`.

## Parity corpus

### Where it lives

| Copy | Path |
| --- | --- |
| Source of truth (server repo) | `viamin/color_matching` → `priv/parity/v1/corpus.json` (deterministic; server CI verifies committed bytes with `mix parity.generate --check`) |
| Vendored fixture (this repo) | `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity-corpus.json` — byte-identical copy |

The fixture is loaded by `SolverParityCorpusTests`
(`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`)
and replayed against `WeightedSquaredErrorScorer` on every `swift test` run:
every per-candidate score must equal the server's expected value (or
`"excluded"`), and the selection must reproduce the server's
**earliest-index-wins** tie-breaking — including the tie, exclusion, and
no-selection scenarios.

### How to refresh

```bash
curl -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity-corpus.json \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json
cd ColorComposerCore && swift test   # SolverParityCorpusTests must be green
```

(Or copy the file from a local server checkout after running
`mix parity.generate` there.)

Refresh triggers:

- The server bumps `algorithm_version` (corpus top level) — every expectation
  moved; refresh the fixture and re-run the parity tests. The metadata test
  fails loudly on any version/policy/scorer mismatch so a stale fixture can't
  pass silently.
- Scoring semantics change server-side without a version bump — the per-score
  assertions fail; treat that as a server bug.

Never hand-edit the fixture: it is generated bytes, compared verbatim with the
server's committed copy.

## Generated OpenAPI client

The structural adoption guards live in
`ColorComposerCore/Tests/ColorComposerCoreTests/OpenAPIClientAdoptionTests.swift`
and expect the standard `swift-openapi-generator` layout:

- `Package.swift` pins `apple/swift-openapi-generator` (plugin) and
  `apple/swift-openapi-runtime` (library),
- an `OpenAPIGenerated` target runs the `OpenAPIGenerator` plugin,
- the document lives at `ColorComposerCore/Sources/OpenAPIGenerated/openapi.yaml`
  (`.yml`/`.json` accepted) and describes the two endpoints `PaletteAPIClient`
  uses today — `GET /api/v1/printer_profiles` and
  `GET /api/v1/colors?printer_profile_id=N` — and nothing more (new API
  surfaces are a non-goal),
- hand-written `Sources/ColorComposerCore` code imports `OpenAPIGenerated`
  (`PaletteAPIClient` migrates to it, or wraps it).

### Refreshing the document

Export the spec from a running server (no auth required for the spec route):

```bash
curl -o ColorComposerCore/Sources/OpenAPIGenerated/openapi.yaml \
  http://localhost:4000/api/v1/openapi.json   # convert JSON→YAML or keep .json
```

The generated client (and the document it comes from) must keep the wire
shapes the existing behavior tests pin: the `printer_profiles` /
`colors` envelopes (snake_case), per-server/profile disk caching
(`ProfileColorCache`), offline-stale fallback, cached profile fallback, and
bearer-token handling — see `PaletteAPIClientTests`, `APIDecodingTests`, and
`ProfileColorCacheTests`.

### Parity findings (corpus v1)

- **Ties:** earliest index wins — exactly `Enum.min_by/3` semantics, matched
  by strict less-than scanning. Covered scenarios: two-way symmetric tie
  (`tie-symmetric-around-target`), duplicate vectors (`tie-duplicate-vectors`),
  and a three-way tie (`tie-three-way-on-lps`, `mixed-large-palette`).
- **Exclusions:** a candidate **or** the target missing any measurement on a
  positive-weight channel excludes that candidate (`missing-candidate-excluded`,
  `missing-target-excluded` — the target-side miss excludes the whole palette,
  `selected_index: null`). Missing is never zero brightness
  (`missing_policy: excluded-when-any-positive-weight-channel-missing`).
- **Weight handling:** the score is the raw weighted **sum** (not a mean) of
  `weight · (candidate − target)²` over positive-weight channels — the Swift
  doctest parity case (`0.205`) matches the Elixir doctest verbatim.
  Zero-weight channels neither contribute nor trigger exclusion
  (`zero-weight-channel-missing`); unknown light-source keys in the weights
  map (e.g. `ultraviolet`) are dropped, not rejected
  (`unknown-weight-ignored`).
