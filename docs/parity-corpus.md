# Solver parity corpus

The macOS app's `WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver so the client and server agree on
selection. The parity corpus is the golden-vector contract that keeps the two
implementations from silently diverging on tie-breaking, missing-measurement
exclusion, or channel weighting.

## Where the corpus lives

- **This repo (consumed by tests):**
  `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/v1/corpus.json`
- **Upstream (source of truth):**
  [`priv/parity/v1/corpus.json`](https://github.com/viamin/color_matching/blob/main/priv/parity/v1/corpus.json)
  in `viamin/color_matching`, generated by `mix parity.generate`
  (issue [viamin/color_matching#111](https://github.com/viamin/color_matching/issues/111),
  merged as [PR #112](https://github.com/viamin/color_matching/pull/112)).

The fixture is a **byte-identical copy** of upstream `algorithm_version: 1`:

## How the tests consume it

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`
replays every scenario and asserts **exact** (bit-for-bit) agreement:

1. **Per-candidate scores** — each expected score is either a finite number or
   `"excluded"`; numbers are compared with exact `Double` equality (corpus
   floats are dyadic rationals, exactly representable in IEEE-754, and both
   implementations accumulate in canonical channel order
   `white → red → green → blue → lps`).
2. **Selection** — scenarios whose target is fully measured on every
   positive-weight channel are replayed end-to-end through
   `CompositionSolver.solve` with a 1×1 grid per active channel, asserting the
   selected palette index, per-cell error, and excluded-candidate count.
   Scenarios whose *target* is missing a positive-weight channel cannot be
   expressed as source grids, so they are asserted at scorer level
   (every candidate `.excluded`, no selection) — exactly the corpus policy.
3. **Tie evidence** — the tied-index set and `tie_broke` flag are recomputed
   from the actual scores (minimum-score holders, earliest index wins) and
   compared to the corpus.

Coverage dimensions asserted present by
`testCorpusCoversTieExclusionAndWeightDimensions`:

- Ties: `tie-symmetric-around-target`, `tie-duplicate-vectors`,
  `tie-three-way-on-lps` (designed ties; two more scenarios tie incidentally —
  5 of 12 scenarios have `tie_broke: true`, including a three-way tie).
- Exclusions: `missing-candidate-excluded`, `missing-target-excluded`,
  `all-excluded`.
- Weight handling: `zero-weight-channel-missing` (missing data on an unweighted
  channel neither excludes nor contributes), `unknown-weight-ignored` (weight
  keys naming unknown light sources are ignored), `single-channel-lps`.

## Parity findings (2026-11-02 replay)

All 12 scenarios match **exactly** (exact IEEE-754 double equality, no
tolerance) against the current Swift implementation — 5 tie-breaking scenarios,
3 exclusion scenarios, zero-weight and unknown-weight handling included.

## Refreshing the corpus

When upstream regenerates the corpus (for example when the algorithm changes
and `algorithm_version` bumps):

```bash
curl -fsSL -o /tmp/corpus.json \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json
sha256sum /tmp/corpus.json   # compare against the table above
cp /tmp/corpus.json \
  ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/v1/corpus.json
```

Then:

1. If `algorithm_version` changed, create `Fixtures/ParityCorpus/v<n>/` instead
   of overwriting, and update the pinned version in
   `testCorpusMetadataPinsAlgorithmAndPolicy` plus the table above.
2. Run `swift test --filter SolverParityCorpusTests`. Any failure is a real
   client/server parity break — fix the divergence, do not adjust expectations.
3. Update the SHA-256 and blob rows in the table above.
