# Solver parity corpus

The macOS client deliberately mirrors the Elixir `ColorMatching.WeightedSquaredError`
solver (`ColorComposerCore`'s `WeightedSquaredErrorScorer` + `CompositionSolver`
selection) so both sides always pick the same palette color. Upstream publishes a
golden-vector corpus that pins that behavior (viamin/color_matching#111, merged as
viamin/color_matching#112); this repo replays it in the `ColorComposerCore` test
suite so silent divergence — on tie-breaking, missing-measurement exclusion, or
channel weighting — fails CI instead of shipping.

## Where the corpus lives

| What | Where |
| --- | --- |
| Source of truth | `viamin/color_matching` → `priv/parity/v1/corpus.json` (generated by `mix parity.generate`; upstream CI enforces byte-identical regeneration) |
| Committed copy used by tests | `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json` (byte-identical) |
| Pinned upstream commit | `a82aec5441d2a7b0100e8c8ab81d573e11ace9b0` (2026-10-10, corpus v1, `algorithm_version: 1`, 12 scenarios) |
| Test | `ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift` |

## What the test asserts

`SolverParityCorpusTests` replays every scenario through
`WeightedSquaredErrorScorer` and through the production `CompositionSolver` fast
path (each scenario expressed as a 1×1 composition) and asserts exact agreement
(tolerance `1e-12`):

- **Selection** — expected `selected_index` and `selected_hex_color`, including the
  no-selection cases (`all-excluded`, `missing-target-excluded`).
- **Minimum error** — expected `error` per scenario; unmatched cells are `.infinity`.
- **Ties** — earliest-index-wins: recomputed `tied_indices` and `tie_broke` must
  match. The corpus contains four tie scenarios (symmetric ±offset around the
  target, duplicate vectors, three-way on a single channel, and a mixed 8-color
  palette with a three-way tie).
- **Exclusions** — per-candidate `scores` entries must match, with `"excluded"`
  exactly where a positive-weight channel is missing (on candidate *or* target);
  missing is never treated as zero brightness.
- **Weights** — zero-weight channels neither exclude nor contribute; unknown
  light-source keys in the weights map (`ultraviolet`) are ignored.
- **Metadata** — `scorer`, `selection` policy, `missing_policy`, `light_sources`,
  and `algorithm_version` are pinned, so a corpus generated under different
  semantics fails loudly instead of replaying to false confidence.

One corpus scenario (`missing-target-excluded`) cannot be expressed through
`CompositionSolver.solve` — the app always supplies a source grid for every
active channel, so a target can never be missing one. Its exclusion semantics
are asserted at the scorer level instead (documented in the test class).

Run just the parity suite:

```bash
cd ColorComposerCore && swift test --filter SolverParityCorpusTests
```

## Refreshing the corpus

```bash
curl -fsSL \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json
```

Then:

1. Update the pinned upstream commit in this document.
2. If `algorithm_version` changed, a solver-semantics change shipped upstream —
   review the upstream release notes **before** adopting; update the version
   expectation in `SolverParityCorpusTests` as part of that review.
3. `cd ColorComposerCore && swift test` must stay green. A refresh that breaks
   parity is a regression to resolve against the upstream change — never relax
   the test to make it pass.
