# Generated OpenAPI client contract

Issue #39 migrates `PaletteAPIClient` from hand-rolled `URLSession` decoding
to a typed client generated by
[`swift-openapi-generator`](https://github.com/apple/swift-openapi-generator)
+ [`swift-openapi-runtime`](https://github.com/apple/swift-openapi-runtime),
from the OpenAPI 3 spec the `color_matching` server publishes
(viamin/color_matching#110). The tests-only change that precedes it pins the
contract the implementation must satisfy.

## What is pinned, and where

All assertions live in `ColorComposerCore/Tests/ColorComposerCoreTests/`.

### 1. The OpenAPI document is committed

- **Path:** `ColorComposerCore/Sources/ColorComposerCore/OpenAPI/openapi.json`
  (JSON, not YAML — it is fetched verbatim from the server and parsed by the
  contract tests with `JSONSerialization`).
- **Refresh:** `curl $SERVER/api/v1/openapi.json -o Sources/ColorComposerCore/OpenAPI/openapi.json`
  (the endpoint is unauthenticated; all other `/api/v1` routes take the
  optional bearer token).
- Enforced by `OpenAPIContractTests.testDocumentIsAnOpenAPI3Spec` and every
  spec-reading test via `requireSpec()`.

### 2. Package wiring

`Package.swift` must declare the `swift-openapi-runtime` dependency and apply
the `OpenAPIGenerator` plugin to the `ColorComposerCore` target. Enforced by
`OpenAPIContractTests.testPackageManifestWiresOpenAPIGeneratorAndRuntime`.

### 3. `/api/v1` shape compatibility

The spec must describe both endpoints the client uses —
`GET /api/v1/printer_profiles` (`PrinterProfilesResponse`) and
`GET /api/v1/colors` (`ColorsResponse`) — with the `bearerAuth` http/bearer
scheme, and the schema property names must cover every coding key the app's
DTOs decode (`printer_profiles`, `printer_profile`, `colors`, `id`, `name`,
`hex`, `rgb`, `palette_id`, `palette_name`, `sort_order`, `responses`).
Enforced by the remaining `OpenAPIContractTests` tests, including a
spec-shaped sample decoded through `ColorsResponse` itself, so a server-side
shape change fails here before it fails in the app.

### 4. Behavior preservation

`PaletteAPIClientWireContractTests` and `OfflineFallbackIntegrationTests`
pin the observable behavior the migration must keep — endpoint paths, the
`printer_profile_id` query, `Accept: application/json`, trimmed-or-absent
bearer tokens, 401/500/malformed-body error mapping, and the
fetch → `ProfileColorCache` disk round-trip that powers per-server/profile
caching, offline-stale badges, and the cached-profile picker fallback. These
pass against the hand-rolled client today and must remain green unchanged
after the migration (wrap the generated client inside `PaletteAPIClient`
rather than changing its public surface).

## Notes for the implementation run

- Keep `PaletteAPIClient`'s public initializers and methods intact; inject or
  construct the generated `Client` internally (`Client(urlSession:)` from
  `swift-openapi-runtime`).
- The generated types replace the hand-rolled envelope decoding, but
  `PaletteColorDTO`/`PrinterProfileDTO` remain the app-facing models —
  convert at the boundary and keep the cache format (snake_case DTO JSON on
  disk) unchanged so existing offline caches keep working.
- If the spec surfaces any `/api/v1` shape difference versus today's DTOs,
  record it in the PR description (issue #39 deliverable) — the
  `OpenAPIContractTests` schema tests are the place it will surface first.
