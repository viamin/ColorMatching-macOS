# Solver parity corpus

`WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver so the macOS client and the
`color_matching` server agree on color selection. The **solver parity
corpus** turns that claim into an executable contract: a committed JSON
snapshot of Elixir solver decisions that the Swift solver must reproduce
exactly — scores, exclusions, weight handling, and tie-breaking.

Upstream source: the corpus is generated by `viamin/color_matching`
(parity corpus PR [#111](https://github.com/viamin/color_matching/pull/111))
against the same OpenAPI-published API surface as spec PR
[#110](https://github.com/viamin/color_matching/pull/110).

## Where the corpus lives

```
ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/solver_parity_corpus.json
```

It is committed verbatim — never hand-edited — so the file always reflects
the Elixir solver's actual output. An alternate location can be supplied
via the `SOLVER_PARITY_CORPUS_PATH` environment variable (useful for
validating a freshly generated corpus before committing it):

```bash
SOLVER_PARITY_CORPUS_PATH=/tmp/solver_parity_corpus.json swift test \
  --filter SolverParityCorpusTests
```

## Schema

```json
{
  "version": 1,
  "generator": "color_matching 1.2.3 (mix solver.parity_corpus)",
  "cases": [
    {
      "id": "tie-earliest-wins",
      "description": "Two colors equidistant from the target.",
      "weights": {"white": 0.5, "red": 1.0, "green": 1.0, "blue": 0.0, "lps": 1.5},
      "palette": [
        {"id": 7, "responses": {"red": 0.4}},
        {"id": 8, "responses": {"red": 0.6}}
      ],
      "target": {"red": 0.5},
      "expected": {
        "selected_color_id": 7,
        "score": 0.01,
        "tie": true,
        "excluded_color_ids": []
      }
    }
  ]
}
```

Rules the consumer (`SolverParityCorpusTests` / `SolverParityRunner`)
enforces:

- `weights`, `palette[].responses`, and `target` use only the canonical
  light-source keys (`white`, `red`, `green`, `blue`, `lps`). Unknown keys
  fail the run — a corpus condition the client cannot express would make
  parity meaningless.
- Weight keys may be omitted (treated as `0`). A weight of `0` makes the
  channel *optional*: candidates missing it stay eligible. Weights `> 0`
  make the channel *required*: a candidate missing any of them is
  excluded, never scored as zero brightness.
- `target` must carry a value for every active (`weight > 0`) condition —
  the solver always builds complete target vectors from source grids.
- `expected.selected_color_id` is `null` when every candidate is excluded.
- `expected.tie` must be `true` exactly when two or more candidates share
  the minimal score; the expected winner is then the **earliest palette
  entry** among the tied candidates (deterministic earliest-wins
  tie-breaking, matching both solvers).
- Scores are IEEE-754 doubles; comparisons use a `1e-9` absolute
  tolerance (summation order may differ), selections must match exactly.

## How the tests consume it

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`:

- `testCommittedCorpusExists` — fails while the corpus is not committed
  (the red-phase signal for this deliverable).
- `testCommittedCorpusMatchesSwiftSolverSelections` — runs every case
  through `WeightedSquaredErrorScorer` **and** a 1×1-grid
  `CompositionSolver.solve`, asserting selection, score, exclusions, and
  tie-winner match the corpus exactly.
- `testCommittedCorpusCoversTiesAndExclusions` — the corpus must keep at
  least one tie case and one exclusion case; a corpus of only
  happy-path unique winners proves nothing.
- `testHarnessVerifiesHandComputedCases` /
  `testHarnessDetectsAMutatedExpectedSelection` — green today; they prove
  the harness is correct and can fail, so corpus failures later mean
  solver drift, not harness bugs.

## Refreshing the corpus

1. Generate the corpus upstream (see the `mix` task added in
   viamin/color_matching#111) from the `color_matching` checkout.
2. Validate it locally before committing:

   ```bash
   SOLVER_PARITY_CORPUS_PATH=/tmp/solver_parity_corpus.json \
     swift test --filter SolverParityCorpusTests
   ```

3. Replace
   `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/solver_parity_corpus.json`
   and commit both the corpus and the `generator` string bump in the same
   change, so every corpus revision is attributable to a server version.

If the Swift solver disagrees with a refreshed corpus, that is a parity
bug: fix the Swift side (or, if the Elixir semantics changed upstream,
mirror the change deliberately) — never edit the corpus to match the
client.
