# Solver parity corpus

`ColorComposerCore` deliberately mirrors the Elixir `ColorMatching.WeightedSquaredError`
solver so the macOS client and the `color_matching` server agree on color selection.
The parity corpus is the executable proof of that mirror: a committed JSON file of
solver inputs together with the expected outputs *produced by the Elixir solver*,
replayed against `WeightedSquaredErrorScorer` in `swift test`.

## Where the corpus lives

```
ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/weighted-squared-error-parity-corpus.json
```

Upstream source: the solver parity corpus exported by
[`viamin/color_matching` #111](https://github.com/viamin/color_matching/pull/111)
(generated by the `ColorMatching.WeightedSquaredError` implementation, selected with
`IlluminantMatching.best_match/4` semantics).

## Contract under test

For each case the corpus fixes:

- **weights** per lighting condition (`white`, `red`, `green`, `blue`, `lps`);
  conditions with weight `> 0` are *required*, weight `0` (or absent) is ignored,
- a **target** brightness vector (a condition may be deliberately absent),
- ordered **candidates**, each with a partial map of measured responses
  (an absent condition means *unmeasured*, never *zero brightness*),
- **expected output**: per-candidate scores (or `null` = excluded), the winning
  score, the selected candidate id (`null` when every candidate is excluded), and
  the ids of tied/excluded candidates.

Selection semantics that must hold exactly:

1. score = `Σ weightᵢ · (candidateᵢ − targetᵢ)²` over conditions with weight `> 0`,
2. a candidate **or** target missing a measurement for any weight-`> 0` condition
   makes that candidate `excluded`,
3. lowest score wins; **ties break to the first candidate in input order**
   (earliest-wins, matching `IlluminantMatching.best_match/4`),
4. a measured brightness of `0.0` scores normally — it is never treated as a
   missing measurement.

## How the tests consume it

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`
loads the fixture and asserts:

- corpus integrity (unique ids, canonical light-source keys, expected blocks
  consistent with the candidate list),
- per-candidate `WeightedSquaredErrorScorer` results match expected scores and
  exclusions (tolerance `1e-12`),
- earliest-wins selection matches the expected candidate, including tie cases,
- the `CompositionSolver` production fast path (1×1 grid) picks the same color,
  error, and excluded-candidate count.

The suite also requires the corpus to keep at least one case of each: a tie,
a candidate exclusion, an all-excluded target, an inactive zero-weight channel
alongside active ones, and all five channels active. An upstream refresh that
drops one of these coverage classes fails the suite.

## Refreshing the corpus

When `color_matching` publishes a new parity corpus artifact:

1. Download the exported corpus JSON from the
   [#111](https://github.com/viamin/color_matching/pull/111) artifact (or regenerate
   it upstream with the export mix task added there).
2. Verify `schema_version` matches what the loader decodes (currently `1`); if the
   schema changed, update the `ParityCorpus` Codable structs in
   `SolverParityCorpusTests.swift` to match and record the change in the PR.
3. Replace the fixture file in `Fixtures/` wholesale — never hand-edit expected
   values; they must originate from the Elixir solver.
4. Run `cd ColorComposerCore && swift test` and confirm
   `SolverParityCorpusTests` is green. Any failure is a genuine client/server
   solver divergence and must be investigated before merging (the algorithm
   itself is intentionally *not* allowed to drift — see the issue #39 non-goals).

The initial corpus committed here was validated by recomputing every expected
value with an independent implementation of the four contract rules above; all
10 cases (3 tie cases, 5 with exclusions, 1 all-excluded, 9 exercising zero-weight
channels, 1 with all five channels active) reproduce exactly.
