# Solver parity corpus & the published `/api/v1` contract

This note covers the two contracts that connect this app to the
[`color_matching`](https://github.com/viamin/color_matching) server:

1. the **solver parity corpus** that pins `WeightedSquaredErrorScorer` to the
   Elixir `ColorMatching.WeightedSquaredError` solver, and
2. the **published OpenAPI 3 spec** for `/api/v1` (viamin/color_matching#110 /
   PR #113) that any generated client here must honor (issue #39).

Both are enforced by tests committed under
`ColorComposerCore/Tests/ColorComposerCoreTests/`. Run them with:

```bash
cd ColorComposerCore && swift test
```

## Solver parity corpus

### Where it lives

- **Upstream (source of truth):** `priv/parity/v1/corpus.json` in
  `viamin/color_matching` (issue #111 / PR #112), generated by
  `mix parity.generate`. The server's CI regenerates it and requires
  byte-identical output (`mix parity.generate --check`), so a given commit's
  corpus is deterministic.
- **This repo (mirror, committed as a test fixture):**
  `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json`
  — a byte-identical copy of upstream `main` at the time of writing
  (SHA-256 `7b7b4d904ff369e1f5be0ec3a994d96cc996056e856d86a2b764b83c050f8604`,
  `algorithm_version: 1`).

The fixture is loaded by `SolverParityCorpusTests.swift` relative to the test
source file (no bundle resource), so `diff` against upstream is always
meaningful.

### What the corpus pins

Each scenario carries palette colors with per-channel response vectors, a
target vector, channel weights, the full per-candidate score table
(`"excluded"` marks missing-measurement exclusions), the expected selection and
error, and explicit tie evidence (`tie_broke`, `tied_indices`). Ties and
no-selection scenarios are intentionally included; the corpus metadata asserts
they stay included.

The test replays every scenario through `WeightedSquaredErrorScorer`, applies
the corpus's `earliest-index-wins` selection, and asserts **exact** agreement —
scores compared with `==` (no epsilon), because every corpus value is a sum of
products of exactly-representable binary fractions; any bit difference is real
algorithm drift. It also guards the `algorithm_version` stamp: when the server
bumps it, every expectation has moved and this app must refresh + reconcile.

### Parity findings (for the #39 PR description)

Current state — **parity holds exactly, no divergence found**:

- All 12 scenarios replay bit-exactly: score tables, selections, errors, and
  tie indices match the Elixir-generated expectations.
- **Ties:** symmetric-around-target, duplicate-vector, and three-way ties all
  resolve to the earliest palette index, matching
  `ColorMatching.IlluminantMatching`'s earliest-wins selection
  (`tie-symmetric-around-target`, `tie-duplicate-vectors`,
  `tie-three-way-on-lps`, `mixed-large-palette`).
- **Exclusions:** a candidate missing a measurement for any channel with
  weight `> 0` is excluded — never treated as zero brightness
  (`missing-candidate-excluded`); a target missing such a channel excludes
  every candidate and leaves no selection (`missing-target-excluded`,
  `all-excluded`, where `selected_index`/`error`/`tie_broke` are `null`).
- **Weight handling:** weight `0` channels neither require measurement nor
  contribute (`zero-weight-channel-missing`); unknown light-source keys in the
  weights map (e.g. `ultraviolet`) are ignored, matching the server's
  `filter_weights/1` (`unknown-weight-ignored`).

### Refreshing the corpus

```bash
curl -fsSL \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json
cd ColorComposerCore && swift test --filter SolverParityCorpusTests
```

- If tests stay green, commit the refreshed fixture.
- If `algorithm_version` changed, `testCorpusAlgorithmVersionIsTheOneThisClientMirrors`
  fails on purpose: update `supportedAlgorithmVersion`, refresh, and reconcile
  any scorer semantic changes in lockstep (out of scope for #39 — the scorer
  algorithm is a non-goal to change).
- Upstream regeneration is `mix parity.generate` (Elixir); determinism is
  enforced by their CI, not ours.

## Published OpenAPI spec for `/api/v1`

The server publishes an OpenAPI 3 document at `GET /api/v1/openapi.json`
(built by `open_api_spex` from `lib/color_matching_web/api_spec.ex` +
`api_schemas.ex`). Until the generated `swift-openapi-runtime` client lands
(#39 implementation phase), a transcription of the two consumed operations is
committed at
`Tests/ColorComposerCoreTests/Fixtures/openapi/v1-openapi.json` and enforced
by `OpenAPISpecConformanceTests.swift`.

### Shape findings (for the #39 PR description)

Comparing the published spec against `PaletteAPIClient`'s hand-written DTOs:

- **No breaking changes found.** The wire shapes the client decodes are the
  shapes the spec declares; spec-conformant payloads round-trip through the
  client today (covered by tests).
- The spec **tightens** several fields the client treats as optional:
  `printer_make_model` / `paper_type` / `ink_type` on `PrinterProfile`, the
  whole `printer_profile` envelope member on `ColorsResponse`, and
  `name` / `palette_id` / `sort_order` on each color item are all `required`
  in the spec but optional in the DTOs. The client is deliberately a tolerant
  superset (also for legacy disk-cache entries); the generated client will
  surface these as non-optional and the wrapper must keep tolerating absence.
- `palette_name` is the one declared-nullable field.
- The per-illuminant `responses` map is `additionalProperties: true` — its
  entry shape (`brightness`, `source`, `raw_value`, `raw_unit`,
  `apparent_brightness`, `measured_at`, `test_run_id`) is controller
  convention, not spec law; the generated client will type it loosely.
- `GET /api/v1/colors` keeps the `printer_profile_id` **query** parameter the
  client sends (required, integer). The router now also offers
  `GET /api/v1/printer_profiles/:id/colors` (`ProfileColorsResponse`, id-less
  color items) — this app does not consume it; adopting it is out of scope for
  #39 per its non-goals.
- Auth: `bearerAuth` (HTTP bearer) on both endpoints, matching the client's
  `Authorization: Bearer …` header.

### Generated-client migration notes (for the #39 PR description)

- Add `swift-openapi-generator` (plugin) + `swift-openapi-runtime` to
  `ColorComposerCore/Package.swift`, generate from the spec (replace the test
  fixture with a package-owned `openapi.yaml` at that point), and migrate or
  wrap `PaletteAPIClient` so `fetchPrinterProfiles`, `fetchColors`, and
  `testConnection` keep their observable behavior.
- The behavior net is already committed: `PaletteAPIClientTests` (11 tests —
  paths, `printer_profile_id` query, trimmed/absent bearer token, JSON Accept
  header, 401 → `.unauthorized`, other non-2xx → `.badStatus`, undecodable
  body → `.malformedResponse`) and `OpenAPISpecConformanceTests` (7 tests).
  They must stay green through the migration, as must `ProfileColorCacheTests`
  (69 tests) which pin the per-server/profile disk cache that feeds the
  offline-stale badges and cached-profile fallback.
- The `algorithm_version` guard and corpus replay are independent of the
  client migration and must remain green too.
