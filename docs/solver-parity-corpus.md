# Solver parity corpus

`WeightedSquaredErrorScorer` (ColorComposerCore) deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver so the client and the
`color_matching` server always agree on palette-color selection. The parity
corpus makes that mirroring an enforced contract instead of a comment: corpus
cases generated by the Elixir solver are replayed against the Swift scorer in
CI, and any divergence — selection, tie handling, exclusion, or score value —
fails `swift test` (issue #39; corpus produced by viamin/color_matching#111).

## Where the corpus lives

```
ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/
├── weighted-squared-error-corpus.json   # canonical corpus from the Elixir service (required)
└── seed-corpus.json                     # hand-computed seed pinning the consumption format
```

The canonical file is **required**: `SolverParityCorpusTests.testCanonicalUpstreamCorpusIsCommitted`
fails while `weighted-squared-error-corpus.json` is absent. `testCommittedCorpusFilesReplayWithExactParity`
replays every `*.json` file in the directory, so the seed validates the harness
and the canonical corpus enforces Elixir/Swift parity.

## Corpus format (version 1)

```json
{
  "version": 1,
  "scorer": "WeightedSquaredError",
  "source": "…",
  "cases": [
    {
      "id": "tie-resolves-to-earliest-position-not-lowest-id",
      "description": "…",
      "weights": { "red": 1.0, "green": 1.0 },
      "target": { "red": 0.5, "green": 0.5 },
      "candidates": [
        { "id": 2, "responses": { "red": 0.4, "green": 0.6 } },
        { "id": 5, "responses": { "red": 0.6, "green": 0.4 } }
      ],
      "expected": { "selected_id": 2, "score": 0.02, "tie": true, "excluded_ids": [] }
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `weights` | Per-light-source weight; light sources are the canonical strings `white`, `red`, `green`, `blue`, `lps` (matching `LightingCondition` raw values). Absent or `0` ⇒ channel inactive. |
| `target` | Desired brightness per light source, normalized `0…1`. An absent key is *missing* (never zero). |
| `candidates[].responses` | Measured brightness per light source (normalized `0…1`); absent ⇒ unmeasured. |
| `expected.selected_id` | Winning candidate id, or `null` when every candidate is excluded. Ties must resolve to the **earliest candidate in array order** (mirrors `CompositionSolver` and the Elixir `IlluminantMatching.best_match/4` policy), not the lowest id. |
| `expected.score` | Optional winning weighted squared error; asserted within `1e-9` when present. |
| `expected.tie` | When `true`, the test asserts another candidate ties the winner and the winner is the earliest of the tied group. When absent/`false`, the test asserts the winner is strictly better, keeping tie markers trustworthy. |
| `expected.excluded_ids` | Candidate ids that must be excluded (missing measurement for a required condition on the candidate **or** the target). |

Unknown light-source keys fail the replay: corpus and `LightingCondition` must
agree.

## How to refresh the corpus

1. Run the corpus generator in a `color_matching` checkout (added by
   viamin/color_matching#111; see that PR for the exact mix task) targeting the
   `WeightedSquaredError` scorer.
2. Copy the emitted JSON over
   `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/weighted-squared-error-corpus.json`
   (keep `version: 1`; bump it only together with changes to this document and
   the harness).
3. Run the parity suite:

```bash
cd ColorComposerCore && swift test --filter SolverParityCorpusTests
```

## Reading a failure

- **Selection mismatch** — the Swift scorer picked a different candidate than
  Elixir. Check weight application and exclusion handling first; both sides
  must treat unmeasured required channels as exclusions, never zero.
- **Tie mismatch** — confirm the corpus candidates are ordered as Elixir fed
  them; parity is with input position (earliest wins), not id order.
- **Score mismatch with matching selection** — floating-point accumulation
  order or weight handling diverged; scores are asserted at `1e-9`.
- **Unknown light source** — the server added an illuminant this client does
  not know; extend `LightingCondition` and `APIModels` first.

The solver algorithm and scorer semantics are intentionally **not** part of
this contract's change surface (issue #39 non-goals): a parity failure means
one side drifted and must be brought back in sync, not that selection policy
should change here.
