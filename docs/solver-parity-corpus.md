# Solver parity corpus

The macOS app's `WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver so client and server agree on
color selection. The parity corpus turns that promise into an executable
contract: the Elixir service generates golden vectors from its own solver,
and this repository replays them through the Swift solver.

## Where the corpus lives

- **Upstream (source of truth):** [`viamin/color_matching`](https://github.com/viamin/color_matching)
  at `priv/parity/v1/corpus.json`, generated by `mix parity.generate`
  (viamin/color_matching#111, merged as #112). Regeneration is deterministic
  and enforced byte-identical in that repo's CI.
- **This repo (consumed copy):** `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json`,
  committed verbatim (no transformations). The corpus carries an
  `algorithm_version` stamp (currently `1`); a bump means the algorithm
  semantics changed and this app needs a conscious review.

## How the tests consume it

`SolverParityCorpusTests` (`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`)
loads the committed corpus and replays **every scenario**:

- **Scorer parity** — per-candidate scores match `expected.scores` exactly
  (numeric scores to `1e-12`; `"excluded"` entries must be excluded), and the
  reconstructed selection (lowest score, *earliest index wins*) matches
  `selected_index`, `error`, `tied_indices`, `tie_broke`, and
  `selected_hex_color`.
- **Solver parity (fast path)** — each solver-expressible scenario is solved
  as a 1×1 composition through `CompositionSolver` with the default scorer;
  the selected palette index, per-cell error, and excluded-candidate count
  must match the corpus.
- **Solver parity (general path)** — the same scenarios solved with a wrapped
  scorer (forcing the general per-candidate path) must select identically, so
  tie-breaking cannot drift between the two solver paths.
- **Coverage guards** — the suite fails if a refreshed corpus drops tie
  cases, exclusion cases, winnerless cases, or unknown-channel-weight cases,
  or stops declaring the canonical five light sources,
  `"excluded-when-any-positive-weight-channel-missing"`,
  `"ColorMatching.WeightedSquaredError"`, and `"earliest-index-wins"`.

Scenarios whose *target* itself misses a positive-weight channel
(`missing-target-excluded`) cannot be expressed through `CompositionSolver`
(grids always supply values); they are replayed at the scorer level only, and
the suite pins exactly which scenario IDs are skipped for that reason.

Set `PARITY_CORPUS_PATH` to replay an arbitrary corpus file (for example a
checkout of the Elixir repo) without touching the committed fixture.

## Refreshing the corpus

```bash
curl -fsSL https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json
swift test --package-path ColorComposerCore
```

Refresh checklist:

1. If `algorithm_version` changed, review the upstream algorithm diff before
   updating `supportedAlgorithmVersion` in `SolverParityCorpusTests`.
2. If scenario IDs changed, update `testOnlyTargetMissingScenariosAreNotSolverExpressible`,
   which intentionally hard-codes the skipped scenario list.
3. Verify the committed copy is byte-identical to upstream (the upstream CI
   guarantees determinism, so any diff is a real semantic change).
