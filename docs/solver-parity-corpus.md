# Solver parity corpus & `/api/v1` contract

This app keeps two unenforced contracts with the [`color_matching`](https://github.com/viamin/color_matching)
server: the palette data it fetches from `/api/v1`, and the solver semantics
its `WeightedSquaredErrorScorer` deliberately mirrors. This document records
how the client consumes the server's published parity corpus and OpenAPI
document, and how to refresh both. (Tracked in issue #39; delivered upstream by
viamin/color_matching#110 and #111.)

## Solver parity corpus

### What it is

A deterministic golden-vector corpus generated by the Elixir server from
`ColorMatching.WeightedSquaredError` + `IlluminantMatching.best_match/3`
(`lib/color_matching/parity/corpus.ex` in the server repo). Every scenario
carries inputs (weights, target vector, palette vectors) and the server's
computed expectations: per-candidate scores or `"excluded"` markers, the
selected index, winning error, tied indices, and tie evidence. The server
regenerates the bytes with `mix parity.generate` and CI verifies them with
`mix parity.generate --check`; the corpus is byte-stable.

### Where it lives here

| Copy | Path |
| --- | --- |
| Upstream source of truth | `viamin/color_matching` → `priv/parity/v1/corpus.json` |
| This repo (test fixture) | `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json` |

The fixture is a byte-for-byte copy (compare SHA-256 when refreshing). The
`v1` path segment mirrors the corpus `algorithm_version`; when upstream bumps
the version, the fixture moves to `Fixtures/parity/v2/…` and
`ParityCorpusFixture.url` (in `ParityCorpus.swift`) is updated with it.

### How the tests consume it

`WeightedSquaredErrorParityCorpusTests` (in
`ColorComposerCore/Tests/ColorComposerCoreTests/`) loads the fixture relative
to `#filePath` — no bundle resources or network needed — and asserts, for
**every** scenario:

- each candidate's score matches exactly (`1e-12`) or is excluded for the same
  reason (missing a positive-weight channel on candidate *or* target);
- selection obeys `earliest-index-wins` — including exact ties
  (`tie-symmetric-around-target`, `tie-duplicate-vectors`,
  `tie-three-way-on-lps`, `zero-weight-channel-missing`, `mixed-large-palette`);
- the winner's hex color, winning error, tied indices, and `tie_broke` flag
  match;
- `CompositionSolver` (the production fast path) reproduces the selection on a
  1×1 grid, including the all-excluded case leaving the cell unmatched. Only
  `missing-target-excluded` is solver-inexpressible (a solver target always
  carries a value per active channel) and is covered at scorer level;
- corpus metadata pins the contract itself: `algorithm_version == 1`, scorer
  `ColorMatching.WeightedSquaredError`, selection `earliest-index-wins`,
  missing policy `excluded-when-any-positive-weight-channel-missing`, light
  sources `[white, red, green, blue, lps]`, and ≥ 12 scenarios retaining tie
  coverage.

### Refreshing the fixture

```bash
curl -fsSL \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json

cd ColorComposerCore && swift test --filter WeightedSquaredErrorParityCorpusTests
```

(Or from a server checkout: run `mix parity.generate` and copy
`priv/parity/v1/corpus.json`.) A refresh that turns the parity suite red means
the server's scoring semantics moved — do **not** adjust the scorer to match
without a coordinated change; upstream bumps `algorithm_version` exactly for
this case.

## `/api/v1` OpenAPI document

The server publishes an OpenAPI 3 document at `GET /api/v1/openapi.json`
(built with OpenApiSpex from `ColorMatchingWeb.ApiSchemas`). The app consumes
two of its operations, both via `PaletteAPIClient`:

- `GET /api/v1/printer_profiles` → `PrinterProfilesResponse`
- `GET /api/v1/colors?printer_profile_id=N` → `ColorsResponse`

`APIv1OpenAPIContractTests` pins the client to the published response schemas
using minimal spec-conformant payloads (required properties only, plus the
spec's `palette_name: null` nullable marker and optional `rgb`), decoded
through the real `PaletteAPIClient` — so migrating to the generated
`swift-openapi-generator` client must keep accepting exactly these shapes.

### Shape audit (2026-11, spec at `main`)

No breaking changes found; the client's DTOs are a lenient subset of the spec:

- `ColorsResponse.printer_profile` is **required** by the spec; the client
  decodes it as optional (still fine — strictness only goes one way).
- Spec-required color fields `name`, `palette_id`, `sort_order` are optional
  in the client DTOs; `hex`/`id` required on both sides.
- `palette_name` is spec-nullable and client-optional; `rgb` is optional in
  both (client falls back to parsing `hex`).
- The spec types `responses` as a free-form object; the client decodes the
  documented per-response shape from color_matching PR #84 (`brightness`,
  `source`, `raw_value`, `raw_unit`, `apparent_brightness`, …) and ignores
  unknown light-source keys.

The generated-client migration (issue #39) should replace the hand-written
transport with types generated from this document while keeping the
disk-cache / offline-stale behavior in `ProfileColorCache` intact — that
behavior is covered by `ProfileColorCacheTests` and is untouched by the
contract tests.
