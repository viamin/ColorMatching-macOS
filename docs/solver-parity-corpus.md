# Solver parity corpus

The `WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver, and `CompositionSolver` mirrors
the earliest-wins selection of `ColorMatching.IlluminantMatching`. The
**parity corpus** is the shared golden-vector fixture, produced upstream by
`ColorMatching.Parity.Corpus`, that both test suites replay so silent
divergence — in tie-breaking, missing-measurement exclusion, or channel
weighting — is caught.

## Where the corpus lives

A verbatim copy of the corpus committed in the backend repo
(`viamin/color_matching`, `priv/parity/v1/corpus.json`, generated by
`mix parity.generate`) is committed in this repo at:

```
ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/corpus.json
```

Keeping the copy inside the test target means `swift test` needs no submodule
checkout or network access.

## What the tests assert

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`
loads the fixture and, for every scenario:

- **Per-candidate scores** match the corpus exactly (including `"excluded"`
  entries). All corpus values are exact binary fractions, so `1e-12`
  tolerance is effectively bit-exact.
- **Selection** matches `expected.selected_index` / `selected_hex_color` /
  `error`, replayed with the earliest-wins rule (`<` keeps the earlier index).
- **Ties**: `tied_indices` and `tie_broke` are recomputed and must match,
  covering symmetric-around-target ties, duplicate-vector ties, and a
  three-way tie on a single channel.
- **Exclusions**: candidates or a target missing any positive-weight channel
  are excluded, never treated as zero brightness; the all-excluded scenario
  yields no selection.
- **Weight handling**: zero-weight channels neither exclude nor contribute;
  unknown weight keys (e.g. `ultraviolet`) are ignored and yield identical
  weights to the equivalent known-key scenario.
- **Solver fast path**: every scenario whose target is fully measured is also
  replayed through `CompositionSolver` on a 1×1 grid, asserting the selected
  index, recorded error (infinite when nothing is selectable), and the
  excluded-candidate diagnostic count. Only `missing-target-excluded` skips
  this replay (the solver requires a grid for every active channel).
- **Metadata contract**: `algorithm_version == 1`, scorer name, the
  `earliest-index-wins` selection policy, the
  `excluded-when-any-positive-weight-channel-missing` missing policy, and the
  light-source set must equal `LightingCondition.allCases`.
- **Scenario IDs** are pinned so silent corpus truncation or reordering fails.

## How to refresh the corpus

The corpus is deterministic upstream: `mix parity.generate` always emits
identical bytes.

1. In a `color_matching` checkout, regenerate and copy the fixture:

   ```bash
   cd color_matching
   mix parity.generate
   cp priv/parity/v1/corpus.json \
     /path/to/ColorMatching-macOS/ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/corpus.json
   ```

2. To preview a fresh corpus before committing it, point the tests at it
   without copying:

   ```bash
   cd ColorComposerCore
   PARITY_CORPUS_PATH=/path/to/color_matching/priv/parity/v1/corpus.json swift test
   ```

3. Refresh deliberately whenever the upstream corpus changes. If
   `algorithm_version` was bumped, scoring semantics moved: review every
   expectation diff before updating the fixture (the metadata test will fail
   until the fixture and this client's scorer semantics are reconciled).

## CI / exit criteria mapping

- `swift test` (ColorComposerCore) runs the parity suite on every build; a
  failing parity test means the mirrored solver or the fixture drifted.
- Issue #39's exit criterion "parity test results" is evidenced by this suite
  passing against corpus `algorithm_version` 1 (12 scenarios).
