# Solver parity corpus

The macOS app's `WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver, and `CompositionSolver` mirrors the
earliest-index-wins selection of `ColorMatching.IlluminantMatching.best_match/4`
— "so client and server agree on selection". Until now nothing *enforced* that;
the two implementations could silently diverge on tie-breaking,
missing-measurement exclusion, or channel weighting. The server now publishes a
deterministic golden-vector corpus, and this repo replays it in its test suite
(viamin/ColorMatching-macOS#39, consuming viamin/color_matching#111).

## Where the corpus lives

- **Upstream (source of truth):** [`priv/parity/v1/corpus.json`][upstream] in
  viamin/color_matching, generated by `mix parity.generate` and committed to the
  repo. The server's CI regenerates it and fails unless the result is
  byte-identical (`mix parity.generate --check`), so the corpus can never drift
  from the Elixir solver that produced it.
- **This repo (committed copy):** `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity-v1-corpus.json`
  — a **byte-identical** copy of the upstream file (sha256 `7b7b4d90…f8604` for
  corpus `algorithm_version` 1, 12 scenarios).

The test target loads the fixture from the path next to
`SolverParityCorpusTests.swift` (via `#filePath`), so it needs no bundle-resource
declaration and works under both `swift test` and Xcode.

## How the tests consume it

`SolverParityCorpusTests` (in `ColorComposerCore/Tests/ColorComposerCoreTests/`)
replays the corpus exactly the way the upstream README prescribes: score every
palette color against each scenario's target using the scenario's weights, then:

1. **Corpus contract** — `algorithm_version`, `scorer`
   (`ColorMatching.WeightedSquaredError`), `selection`
   (`earliest-index-wins`), `missing_policy`
   (`excluded-when-any-positive-weight-channel-missing`), and the canonical
   light-source set must all match what this package implements. The suite also
   fails if a refreshed corpus drops coverage of ties, exclusions, or
   no-selection scenarios (current floor: ≥ 12 scenarios, ≥ 5 ties, ≥ 4 with
   exclusions, ≥ 2 with no selection).
2. **Score table parity** — every candidate's score matches the recorded golden
   vector (`1e-12` tolerance; corpus values are dyadic rationals exactly
   representable as `Double`s, so this is effectively bit-exact), and every
   `"excluded"` entry comes back as `.excluded`.
3. **Selection, tie-break, error, hex parity** — earliest index attaining the
   minimum score wins; `selected_index`, `selected_hex_color`, `error`,
   `tied_indices`, and `tie_broke` all agree. Scenarios where every candidate is
   excluded select nothing.
4. **Solver replay** — every scenario whose target carries all active channels
   (11 of 12) is also replayed through `CompositionSolver` with 1×1 source
   grids, verifying the optimized contiguous fast path — and its earliest-wins
   tie-breaking — agrees with the corpus, including the excluded-candidate
   count. (The one scenario whose *target* is missing an active channel cannot
   be expressed as source grids — grids always provide every active channel —
   and is covered by the scorer-level assertions.)

## How to refresh the corpus

When the server's solver changes, upstream regenerates the corpus (bumping
`algorithm_version` when expectations move) and this repo follows:

```bash
curl -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity-v1-corpus.json \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json
cd ColorComposerCore && swift test
```

Rules:

- The copy must stay **byte-identical** to `priv/parity/v1/corpus.json` — never
  hand-edit it; refresh it wholesale so the two repos' copies remain
  diff-comparable.
- A changed `algorithm_version` means every expectation has moved: re-verify
  parity in the same change that updates the fixture. `testCorpusMetadataMatchesSwiftSolverContract`
  fails loudly until then.
- Run `swift test` after every refresh. All parity tests must stay green; a
  failure is a genuine client/server divergence (tie-breaking, exclusion
  policy, or weighting) — not a flake.

## Parity findings at adoption (algorithm_version 1)

Verified against the committed corpus (12 scenarios):

- **Ties (5 scenarios):** two-way symmetric-around-target ties, duplicate
  response vectors, and a three-way tie on a single active channel all resolve
  to the earliest palette index — matching `CompositionSolver`'s strict
  `sum < bestError` earliest-wins comparison. No divergence found.
- **Exclusions (4 scenarios):** a candidate missing a positive-weight channel is
  excluded, never treated as zero brightness; a *target* missing a positive-weight
  channel excludes every candidate (no selection); zero-weight channels neither
  exclude nor contribute (a missing channel and a wildly different one tie
  exactly). Matches `WeightedSquaredErrorScorer`'s policy exactly.
- **Weight handling:** unknown light sources in the weights map (e.g.
  `ultraviolet`) are ignored rather than rejected; weights scale squared errors
  linearly (lps 1.5 ≫ blue 0.25 in the standard scenario). Matches.

The Swift scorer's scores are bit-identical to every recorded golden vector.
