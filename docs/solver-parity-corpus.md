# Solver parity corpus

`WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver so the macOS client and the
`color_matching` server agree on color selection. The parity corpus
(generated by the Elixir implementation, viamin/color_matching#111) is the
executable proof that the two agree, and this app consumes it as a committed
test fixture (issue #39).

This document is the in-repo reference for corpus consumption; the same
content should be folded into the top-level README when the corpus lands.

## Where the corpus lives

The corpus is committed as JSON at:

```
ColorComposerCore/ParityCorpus/solver_parity_corpus.json
```

The parity test (`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`)
resolves that path relative to the package root. Two fallbacks exist:

1. `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/solver_parity_corpus.json`
   — a fixture copy, useful for local experiments.
2. The `COLOR_MATCHING_PARITY_CORPUS` environment variable — an absolute path
   to a corpus file, used to validate a freshly generated corpus without
   copying it into the repo:

   ```bash
   COLOR_MATCHING_PARITY_CORPUS=/tmp/solver_parity_corpus.json \
       swift test --filter SolverParityCorpus
   ```

## Corpus schema (version 1)

```json
{
  "version": 1,
  "cases": [
    {
      "id": "tie-symmetric-pair",
      "description": "Two colors equidistant from the target on the only weighted channel; earliest wins. Green (weight 0) differences must not matter.",
      "weights": { "red": 1.0, "green": 0.0 },
      "palette": [
        { "id": 11, "hex": "#0A0A0A", "responses": { "red": { "brightness": 0.4 }, "green": { "brightness": 0.2 } } },
        { "id": 12, "hex": "#0B0B0B", "responses": { "red": { "brightness": 0.6 }, "green": { "brightness": 0.4 } } },
        { "id": 13, "hex": "#0C0C0C", "responses": { "green": { "brightness": 0.9 } } }
      ],
      "target": { "red": 0.5, "green": 0.3 },
      "expected": {
        "selected_color_id": 11,
        "score": 0.01,
        "tie": true,
        "tied_color_ids": [11, 12],
        "excluded_color_ids": [13]
      }
    }
  ]
}
```

Worked through: only `red` has weight > 0, so both 11 and 12 score
`(0.4 − 0.5)² = (0.6 − 0.5)² = 0.01` — a tie resolved to 11, the earliest
palette entry; 13 never measures `red`, so it is excluded rather than treated
as zero; and the green differences (0.2/0.4 vs. target 0.3) are invisible
because green's weight is zero.

- Condition keys are exactly the server's light-source strings — `white`,
  `red`, `green`, `blue`, `lps`. Unknown keys fail the run.
- `weights`: absent keys mean weight `0`. At least one weight must be
  positive per case; the corpus must contain at least one case with an
  explicit `0` value to cover zero-weight handling.
- `palette[].responses`: absent conditions are *missing measurements*, never
  zero brightness. `id` values must be unique within a case; `hex` must be a
  parseable `#RRGGBB` value.
- `target`: a brightness per condition. Every weight > 0 condition must be
  present.
- `expected`:
  - `selected_color_id` — the exact selection, or `null` when every
    candidate is excluded (no eligible match).
  - `score` — the winner's weighted squared error (compared with tolerance
    `1e-9`).
  - `tie` — `true` when multiple eligible candidates share the minimal
    score. Both implementations resolve ties to the **earliest entry in
    palette order**, so `selected_color_id` must be that entry.
  - `tied_color_ids` — all minimal-score candidates (required when
    `tie` is `true`); each must be eligible and share the winning score.
  - `excluded_color_ids` — candidates that must score `.excluded` (missing a
    measurement for a weight > 0 channel). The corpus must contain at least
    one non-empty case, and at least one `tie: true` case overall.

## What the test asserts

`swift test --filter SolverParityCorpus` runs three checks:

1. **Structure** — the corpus is committed, decodes, `version == 1`, case ids
   are unique, every case converts to the solver's domain models, and the
   tie / exclusion / explicit-zero-weight coverage requirements above hold.
2. **Scorer parity** — for every case, replaying `WeightedSquaredErrorScorer`
   over the palette in order (earliest-wins on ties) selects exactly
   `selected_color_id` with the expected score; tie cases additionally
   verify shared winning scores and earliest-entry resolution; cases flagged
   `tie: false` verify no unflagged ties hide in the palette; excluded ids
   verify the missing-measurement exclusion policy.
3. **Solver parity** — the same cases run through `CompositionSolver`'s
   optimized fast path (1×1 source grids per active channel) and must select
   the same color, or leave the cell unmatched when `selected_color_id` is
   `null`.

## Refreshing the corpus

1. Generate a fresh corpus from the Elixir side (the generator lands with
   viamin/color_matching#111).
2. Point the test at it first, without touching the committed file:

   ```bash
   COLOR_MATCHING_PARITY_CORPUS=/path/to/fresh/solver_parity_corpus.json \
       swift test --filter SolverParityCorpus
   ```

3. On green, copy the file over
   `ColorComposerCore/ParityCorpus/solver_parity_corpus.json`, commit it, and
   re-run `swift test` (the committed corpus is what CI enforces).

A red corpus run means client and server disagree on selection — ties,
exclusions, or weight handling have drifted. Fix the *cause*; never edit the
corpus to match the client, and never change the scorer to match a stale
corpus without re-generating it from the Elixir implementation.
