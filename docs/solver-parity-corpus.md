# Solver parity corpus consumption

`ColorComposerCore` enforces parity between the macOS app's
`WeightedSquaredErrorScorer` and the Elixir `ColorMatching.WeightedSquaredError`
solver by replaying a committed golden-vector corpus produced by the
`color_matching` server (viamin/color_matching#111).

## Where the corpus lives

- **Upstream (source of truth):** `priv/parity/v1/corpus.json` in
  [`viamin/color_matching`](https://github.com/viamin/color_matching), generated
  deterministically by `ColorMatching.Parity.Corpus` with `mix parity.generate`
  and byte-verified upstream in CI (`mix parity.generate --check`).
- **This repo (consumed copy):**
  `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/v1/corpus.json`
  — a verbatim copy. One directory per `algorithm_version` (`v1/`, later `v2/` …);
  the test discovers every `*/corpus.json` under `Fixtures/ParityCorpus/`.

## How to refresh the corpus

```bash
curl -fsSL \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/v1/corpus.json \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json
```

Refresh whenever the upstream corpus changes. If upstream bumps
`algorithm_version`, scorer semantics changed: add a new versioned directory,
update the version assertion in `SolverParityCorpusTests`, and expect parity
failures until the Swift scorer is aligned.

> Note: `swift-openapi-generator` and the corpus fixture's resource declaration
> in `Package.swift` land with the implementation phase of issue #39; the test
> reads the fixture from the source tree (`#filePath`-relative), so no manifest
> change is required for the replay to run.

## Corpus schema (algorithm_version 1)

Top level: `algorithm_version`, `scorer` (`ColorMatching.WeightedSquaredError`),
`selection` (`earliest-index-wins`), `missing_policy`
(`excluded-when-any-positive-weight-channel-missing`), `light_sources`
(`white red green blue lps`), and `scenarios[]`. Each scenario carries:

| Field | Meaning |
| --- | --- |
| `id`, `description` | Stable scenario name and intent |
| `weights` | Map of light source → weight; unknown sources (e.g. `ultraviolet`) are ignored, weight `0` channels are ignored entirely |
| `target` | `{ hex_color, channels }`; an absent channel key means *unmeasured*, never zero |
| `palette[]` | Ordered candidates; order defines the tie-break |
| `expected.scores[]` | Per-candidate score, or the string `"excluded"` |
| `expected.selected_index` / `selected_hex_color` / `error` | Winning candidate (`null` when all are excluded) and its score |
| `expected.tie_broke` / `tied_indices` | Whether the minimum was tied, and every index achieving it |

## What the parity test asserts

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`:

1. The fixture is committed and stamped (`algorithm_version`, scorer, selection
   policy, light sources).
2. Coverage scenarios are present: exact ties (symmetric, duplicate vectors,
   three-way), candidate/target exclusion, all-excluded, zero-weight-channel
   missing data, unknown weight keys, and a mixed large palette.
3. Every scenario replays with exact agreement: per-candidate scores
   (`1e-12`), exclusion, selection index and hex color, winning error, tie
   indices, and the `tie_broke` flag — under the same earliest-index-wins
   policy as `IlluminantMatching.best_match/3`.

Parity findings to date: the Swift scorer matches the corpus on all 12
scenarios — ties break to the earliest palette index, missing measurements on
positive-weight channels exclude (never count as zero), zero-weight and unknown
channels neither exclude nor contribute.

# OpenAPI document

Issue #39 also migrates `PaletteAPIClient` onto a typed client generated by
`swift-openapi-generator` from a committed OpenAPI document exported from the
server's `ColorMatchingWeb.ApiSpec` (viamin/color_matching#110; it documents
`/api/v1/printer_profiles`, `/api/v1/colors?printer_profile_id=`, and the
`bearerAuth` scheme).

- Expected location: `ColorComposerCore/Sources/ColorComposerCore/OpenAPI/openapi.yaml`
  (`.yml`/`.json` accepted).
- `OpenAPIClientMigrationTests` enforces: the document is committed, describes
  both `/api/v1` endpoints, the `printer_profile_id` query parameter, and
  bearer auth; `Package.swift` declares `swift-openapi-generator` and
  `swift-openapi-runtime`.
- `PaletteAPIClientTests` pins the existing wire behavior (request targets,
  query spelling, `Accept` header, envelope mapping) so the generated-client
  migration cannot change what goes over the wire. The disk cache
  (`ProfileColorCacheTests`) and offline-stale/cached-profile fallback behavior
  are unchanged by design.
