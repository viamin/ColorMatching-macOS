# Solver parity corpus & the `/api/v1` generated client

This note covers the two contracts that connect this app to the
[`color_matching`](https://github.com/viamin/color_matching) server: the
**solver parity corpus** that pins `WeightedSquaredErrorScorer` to the Elixir
`ColorMatching.WeightedSquaredError` solver, and the **OpenAPI-generated
client** migration of `PaletteAPIClient`.

## Solver parity corpus

### Where the corpus lives

- **Canonical source (upstream):** `priv/parity/v1/corpus.json` in
  `viamin/color_matching`, generated by `mix parity.generate` and certified by
  that repo's ExUnit corpus + property suites (viamin/color_matching#111,
  merged as #112). It carries an `algorithm_version` stamp (currently `1`),
  the scorer id (`ColorMatching.WeightedSquaredError`), the selection policy
  (`earliest-index-wins`), and the missing-measurement policy
  (`excluded-when-any-positive-weight-channel-missing`).
- **Committed copy (this repo):**
  `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/v1/corpus.json`
  — byte-identical to upstream
  (sha256 `7b7b4d904ff369e1f5be0ec3a994d96cc996056e856d86a2b764b83c050f8604`).

### How the tests consume it

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`
replays every scenario twice:

1. **Scorer-level** — each candidate's `WeightedSquaredErrorScorer` score (or
   `.excluded`) must equal the corpus value, and the tie set, `tie_broke`
   flag, earliest-wins winner, selected hex, and winning error must all agree.
   The corpus deliberately contains exact ties (`tie-symmetric-around-target`,
   `tie-duplicate-vectors`, `tie-three-way-on-lps`), missing-measurement
   exclusions (candidate- and target-side), a zero-weight-channel case, an
   unknown-weight-key probe (`ultraviolet`), and an all-excluded case.
2. **Solver-level** — each solvable scenario is solved through
   `CompositionSolver` on a 1×1 grid (the production contiguous fast path);
   the selected palette index, per-cell error, unmatched-cell outcome, and
   excluded-candidate count must match the corpus. This is what keeps the
   solver's inline math from drifting away from the scorer the corpus
   certifies.

A corpus-stamp test additionally fails loudly when upstream bumps
`algorithm_version` or changes the certified scorer/selection/missing policy,
so a fixture refresh is always a conscious decision.

The fixture loads from the checkout path next to the test file; if it is
later declared as a package resource (`.copy("Fixtures")` on the test target
in `ColorComposerCore/Package.swift`), the loader's bundle fallback picks it
up without test changes.

### How to refresh the corpus

```bash
curl -fsSL \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/ParityCorpus/v1/corpus.json
swift test --package-path ColorComposerCore --filter SolverParityCorpusTests
```

If upstream publishes a new version directory (`priv/parity/v2/…`), add it as
a *new* fixture directory rather than overwriting `v1`, bump the expected
`algorithmVersion` in the stamp test, and migrate scenarios in one conscious
change.

## OpenAPI-generated client migration

The server publishes an OpenAPI 3 document at `GET /api/v1/openapi.json`
(viamin/color_matching#110). `ColorComposerCore` is adopting
`swift-openapi-generator` + `swift-openapi-runtime`: a typed client is
generated from that document and `PaletteAPIClient` migrates onto it (or wraps
it) without changing its observable behavior.

The migration guardrails are
`ColorComposerCore/Tests/ColorComposerCoreTests/PaletteAPIClientMigrationContractTests.swift`,
which pin today's externally observable contract — request shapes
(`/api/v1` base path, `printer_profile_id` query, `Accept: application/json`,
normalized bearer token), wire decoding (snake_case envelopes, null/
absent `printer_profile`, unknown light-source keys tolerated until domain
conversion, forward-compatible with spec-added fields), and the error taxonomy
(`401 → .unauthorized`, other non-2xx → .badStatus`, undecodable body →
`.malformedResponse`). These must stay green across the migration so the
per-server/profile disk cache, offline-stale badges, and cached-profile
fallback in `ColorCatalog`/`ProfileColorCache` (covered by
`ProfileColorCacheTests.swift`) behave exactly as before.
