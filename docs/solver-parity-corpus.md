# Solver parity corpus

`WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver in
[`color_matching`](https://github.com/viamin/color_matching) so the macOS
client and the server always agree on color selection. The parity corpus
turns that claim into an executable contract.

## Where the corpus lives

```
ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/solver_parity_corpus.json
```

It is committed with the repo and consumed by
`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`,
which runs every case twice:

1. **Scorer parity** — a best-match harness replicates the Elixir
   `IlluminantMatching.best_match/4` loop over `WeightedSquaredErrorScorer`
   and asserts the selected color id, winning score, excluded candidates,
   and tie set all match the corpus exactly.
2. **Solver parity** — the same case is solved through
   `CompositionSolver`'s optimized contiguous fast path on a 1×1 grid and
   must pick the same palette index (and excluded count), pinning the fast
   path to the same policy as the scorer.

Run them with:

```bash
cd ColorComposerCore && swift test --filter SolverParityCorpus
```

## What each case encodes

Each case is a palette, a target brightness vector, channel weights, and the
expected outcome:

| Field | Meaning |
| --- | --- |
| `weights` | Per-channel weights; `0`/absent channels are ignored and **not** required |
| `palette[].responses` | Measured brightness per lighting condition; absent = unmeasured |
| `target` | Desired brightness per condition |
| `expected.selected_id` | Winning color id (`null` when everything is excluded) |
| `expected.score` | Winner's weighted squared error (1e-9 tolerance) |
| `expected.excluded_ids` | Candidates excluded for missing a required measurement |
| `expected.tied_ids` | Candidates scoring exactly like the winner — the earliest palette position must win |
| `solver_check` | `false` to skip the solver cross-check (scorer-level edge cases only) |

The corpus intentionally covers: the Elixir doctest values, exact matches,
**measured zero ≠ missing**, candidate/target exclusion, zero-weight channels,
two- and three-way ties, weight-driven winner flips (equal vs heavy weights
on the same palette), fractional weights, and all-excluded palettes.

## Provenance and refreshing

The initial corpus shipped here was hand-derived from the published
`WeightedSquaredError` semantics — the Elixir doctest and the selection
policy documented in both repositories — and every expected value was
independently recomputed before commit.

The canonical corpus is generated by the `color_matching` server
(viamin/color_matching#111). To refresh:

1. Generate the corpus on the server side (see that repo's parity corpus
   task/docs) — it emits the same JSON schema (`version`, `scorer`,
   `source`, `selection_policy`, `cases`).
2. Replace the fixture file above with the generated output. Keep the file
   name; the test locates it relative to the test source.
3. Add cases only through regeneration — never hand-edit expected outputs to
   make a failing test pass; a mismatch means client and server disagree and
   must be resolved on one side or the other.
4. Re-run `swift test --filter SolverParityCorpus` (macOS/Xcode required;
   the fixture loads from the source tree, no bundle resources needed).

The shape test (`testCorpusFileExistsAndIsValidates`) guards the schema: it
rejects unknown lighting conditions, duplicate case/palette ids, unparseable
hex, empty palettes, weightless cases, and tie sets that do not contain the
winner — so a malformed refresh fails loudly instead of silently weakening
coverage.
