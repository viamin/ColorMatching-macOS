# Solver parity corpus

The macOS app's `WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver so client and server agree on
selection. The parity corpus — generated by the server (viamin/color_matching#111)
— is the machine-checked proof that they still do.

## Where the corpus lives

| Copy | Path |
| --- | --- |
| Consumed by tests | `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity-v1-corpus.json` |
| Generated upstream | `priv/parity/v1/corpus.json` in [viamin/color_matching](https://github.com/viamin/color_matching) |

The fixture is a **byte-identical** copy of the upstream corpus at the pinned
commit recorded below. It is loaded from disk next to the test source (via
`#filePath`), so it runs identically under `swift test` on macOS and under the
`bin/lint` portable-subset harness on Linux.

## How to refresh

```bash
curl -fsSL \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity-v1-corpus.json
sha256sum ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity-v1-corpus.json
```

Then update the pinned commit / SHA-256 above and run `swift test`. If the
scenario count changed, `SolverParityCorpusTests.testCorpusFixtureIntegrity`
fails on purpose — review the new scenarios before accepting the new count.
A corpus whose `algorithm_version` bumped means the server algorithm changed
semantically; treat any mismatch as a parity break first, not as a refresh.

## What the test enforces

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`
replays every scenario two ways and demands exact agreement:

1. **Scorer level** — every candidate is scored with
   `WeightedSquaredErrorScorer.score(candidate:target:weights:)`; scores must
   equal the corpus values (tolerance `1e-12`; corpus values are exact dyadic
   fractions), `excluded` outcomes must match `"excluded"` entries, and the
   selection must be the **earliest index** achieving the minimum score.
2. **Solver level** — each scenario also runs through the production
   `CompositionSolver.solve` fast path with 1×1 source grids, asserting the
   selected palette index and per-cell error, so parity covers the app's real
   selection path. (Scenarios whose *target* is missing a positive-weight
   channel are scorer-level only: the solver always builds complete targets
   from source grids.)

Tie evidence is recomputed from the scores and must match `tied_indices`,
`tie_broke`, and `selected_index` exactly.

## Corpus scenario inventory (v1)

12 scenarios: distinct errors; symmetric two-way tie; duplicate-vector tie;
three-way tie on a single channel; candidate-missing exclusion; target-missing
exclusion (no selection); zero-weight channel missing (must **not** exclude);
all-excluded (no selection); single-channel match; exact match at zero error;
unknown weight key ignored; mixed 8-color palette.

### Parity findings (verified at the pinned corpus)

- **Ties**: earliest-index-wins, deterministic, including a three-way tie —
  matches `CompositionSolver`'s strict `<` comparison in candidate order.
- **Exclusions**: a candidate missing *any* positive-weight channel is
  excluded, never treated as zero brightness; a target-side gap excludes
  every candidate. Zero-weight channels never cause exclusion.
- **Weight handling**: only the canonical five light sources
  (`white`, `red`, `green`, `blue`, `lps`) influence matching; other keys in
  the weights map (e.g. `ultraviolet`) are ignored.
- An offline replay of the same algorithm over the corpus agrees **12/12**
  with the expected selections, scores, and tie sets (see the parity test).
