# Solver parity corpus & OpenAPI client consumption

Issue #39 wires this app to the two contracts the `color_matching` service
publishes: the **OpenAPI 3 spec** for `/api/v1` (viamin/color_matching#110)
and the **solver golden-vector corpus** for `WeightedSquaredError`
(viamin/color_matching#111). This note records where both artifacts live in
this repo, how to refresh them, and what the tests enforce. The README
section promised by the issue is added in the implementation run; this file
is the authoritative detail behind it.

## Solver parity corpus

### Where it lives

| What | Path |
| --- | --- |
| Committed corpus (this repo) | `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json` |
| Upstream source of truth | `priv/parity/v1/corpus.json` in viamin/color_matching (generated by `mix parity.generate`) |
| Parity suite | `ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift` |

The fixture is a **byte-identical copy** of upstream `priv/parity/v1/corpus.json`
(verified with an independent replay, see "Parity findings" below). It is
versioned by the corpus's own `algorithm_version` stamp (currently `1`); when
upstream bumps the version, copy the new file into a new `parity/v2/` fixture
directory, point the suite at it, and review the diff — never hand-edit cases.

### How to refresh

```bash
curl -sfL -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json
```

Then run `swift test --package-path ColorComposerCore` (the corpus metadata
test fails loudly on an `algorithm_version` bump, which is the signal to
review rather than blindly refresh).

Note for the implementation run: declare the fixture in the test target
(`.copy("Fixtures")` in `Package.swift`) so SwiftPM stops warning about the
unhandled resource; the suite loads it via `#filePath`-relative lookup, which
works either way.

### What the suite asserts

`SolverParityCorpusTests` replays every scenario through both
`WeightedSquaredErrorScorer` (per-candidate) and `CompositionSolver`
(1×1 grid, exercising the fast path) and requires **exact** agreement:

- every per-candidate score matches `expected.scores` (numbers to 1e-12;
  `"excluded"` entries must come back `.excluded`),
- the selected index matches `expected.selected_index` under the corpus's
  `earliest-index-wins` policy — including the deliberate tie cases
  (`tie-symmetric-around-target`, `tie-duplicate-vectors`,
  `tie-three-way-on-lps`, `zero-weight-channel-missing`, `mixed-large-palette`),
- `tied_indices` / `tie_broke` evidence matches the recomputed tie set,
- the winning error matches `expected.error`,
- no-selection scenarios (all candidates excluded) leave the cell unmatched,
- unknown weight keys (e.g. `ultraviolet`) activate no channel,
- the corpus retains its tie/exclusion/weighting scenario coverage, so a
  regenerated corpus that silently drops cases fails the suite.

Target-driven exclusion (`missing-target-excluded`) is asserted at scorer
level only: solver targets are built from grids and always carry every active
condition, so that policy is not reachable through `solve`.

## OpenAPI generated client

### Spec source and location

The service serves the spec at **`GET /api/v1/openapi.json`** (open_api_spex).
Commit it at `ColorComposerCore/OpenAPI/openapi.yaml` (JSON accepted; the
migration guard accepts the conventional spellings). Refresh:

```bash
curl -sfL <server-base-url>/api/v1/openapi.json \
  -o ColorComposerCore/OpenAPI/openapi.json
```

`GeneratedClientMigrationGuardTests` enforces that a committed document
exists and still describes `/api/v1/printer_profiles` and `/api/v1/colors`,
and that `ColorComposerCore/Package.swift` declares `swift-openapi-generator`
and `swift-openapi-runtime`.

### Migration notes (for the implementation run)

- `swift-openapi-generator` runs as a build-tool plugin over the committed
  document; `PaletteAPIClient` wraps the generated `Client` so its public
  surface (`fetchPrinterProfiles`, `fetchColors`, `testConnection`,
  `PaletteAPIError`) stays unchanged — `ColorComposerCore` is the only
  consumer (`ColorMatching/Networking/ColorCatalog.swift`).
- `PaletteAPIClientMigrationTests` pins the wrapped behavior: request shape
  (`/api/v1/colors?printer_profile_id=N`, `Accept: application/json`),
  bearer-token handling (trimmed, omitted when blank), error mapping
  (401 → `.unauthorized`, other non-2xx → `.badStatus`, undecodable body →
  `.malformedResponse`), and snake_case envelope decoding including a
  tolerated absent `printer_profile`. The migration must keep it green.
- Disk-cache/offline behavior is untouched by design: `ProfileColorCache`
  stores wire DTOs, and `ProfileColorCacheTests` (81 tests: per-server
  namespacing, staleness markers, clear-cache, corrupt-file misses) plus the
  client contract tests are the regression net.

### `/api/v1` shape findings (from the published spec)

Compared against the service's `ApiSchemas` (PR viamin/color_matching#112
lineage), the shapes the app decodes today remain compatible — no breaking
change found:

- `PrinterProfile` marks `printer_make_model`, `paper_type`, `ink_type`
  **required** upstream; the app's DTO treats them optional (more lenient —
  safe).
- `ColorsResponse` marks `printer_profile` required; the app tolerates its
  absence (safe; the disk cache also stores it as optional).
- Upstream types `responses` as a free-form object
  (`additionalProperties: true`) while the app requires each entry to carry
  `brightness`. Soft risk only: the controllers emit `brightness` today, but
  the spec under-specifies the value shape — worth an upstream follow-up.
- `rgb` is optional and `palette_name` nullable upstream, matching the app.

## Parity findings (red-phase evidence)

- An independent replay of the committed corpus (Python, mirroring the Swift
  scorer semantics: positive-weight channels required on both candidate and
  target, sum of `weight·(candidate−target)²`, earliest-index tie-break)
  reproduced **all 12 scenarios exactly** — per-candidate scores, selections,
  tie sets, and `tie_broke` flags. No divergence between the corpus and
  `WeightedSquaredErrorScorer` semantics exists as of this fixture.
- Tie policy confirmed shared: strict-improvement selection keeps the
  earliest index, matching `IlluminantMatching.best_match/4`.
- Exclusions confirmed shared: a color missing any positive-weight channel is
  excluded (never treated as zero brightness); zero-weight channels neither
  exclude nor contribute.
- Weights confirmed shared: per-channel weights scale squared error
  linearly; unknown weight keys are inert.

Swift execution of the suite requires a macOS toolchain, which this Linux
container lacks; CI (or a local `swift test --package-path ColorComposerCore`)
is the executor of record.
