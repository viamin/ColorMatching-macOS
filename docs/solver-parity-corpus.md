# Solver parity corpus

The app mirrors the `color_matching` backend's illuminant solver
(`ColorMatching.WeightedSquaredError` plus the earliest-wins selection of
`ColorMatching.IlluminantMatching`). Nothing in the protocol forces the two
implementations to agree, so the backend publishes a **golden-vector corpus**
and this app replays it as a test.

## Where the corpus lives

| | Path |
| --- | --- |
| Upstream (source of truth) | [`viamin/color_matching`](https://github.com/viamin/color_matching) → `priv/parity/v1/corpus.json` |
| Committed copy (this repo) | `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json` |

The upstream file is generated by `mix parity.generate` (upstream task
`ColorMatching.Parity.Generate`) and is byte-deterministic: the same solver
always produces the same corpus.

## The contract the corpus pins

Every scenario in the corpus is one target response vector, a palette of
candidate response vectors, a weight per light source, and the server's
expected outcome. The corpus header states the contract it encodes:

- `scorer`: `ColorMatching.WeightedSquaredError`
- `selection`: `earliest-index-wins`
- `missing_policy`: `excluded-when-any-positive-weight-channel-missing`
- `light_sources`: `white`, `red`, `green`, `blue`, `lps`

Concretely, the mirrored scorer must:

- sum `weight * (candidate − target)²` over the channels whose weight is
  greater than zero (a **sum**, not a mean);
- **exclude** a candidate that is missing a measurement for any channel with
  a positive weight — missing data is never treated as zero brightness;
- **exclude** every candidate when the *target* is missing such a channel;
- ignore channels whose weight is zero (missing data on them neither excludes
  a candidate nor contributes to the score) and ignore weight entries for
  light sources that do not exist (the corpus carries an `ultraviolet` weight
  on purpose);
- select the lowest score and break ties by the **earliest** candidate index.

## What the test asserts

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`
replays the corpus:

| Test | Asserts |
| --- | --- |
| `testCommittedCorpusMatchesThePublishedFingerprint` | the committed bytes still match the upstream artifact |
| `testCorpusDescribesThePublishedSolverContract` | the corpus header still describes the contract above |
| `testCorpusCoversTiesExclusionsAndWeightHandling` | the scenario set still covers ties, exclusions and weight handling |
| `testScorerScoresMatchCorpusExpectations` | every candidate scores exactly like the server's scorer, exclusions included |
| `testScorerSelectionMatchesCorpusExpectations` | the selected candidate, its hex color and its error match |
| `testTieEvidenceMatchesCorpusExpectations` | the tied candidate set matches, so tie-breaking cannot drift |
| `testTieScenariosSelectTheEarliestTiedCandidate` | every tie resolves to the earliest tied candidate |
| `testSolverSelectsTheCorpusWinner` | the full `CompositionSolver` (the path the app takes) lands on the corpus winner |
| `testSolverLeavesUnmatchedCellsWhenEveryCandidateIsExcluded` | a fully excluded palette produces no selection |

## Refreshing the corpus

1. Fetch the upstream corpus:

   ```bash
   curl -sSL https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
     -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json
   ```

2. Recompute the fingerprint the test pins and update
   `ParityCorpusFixture.expectedFingerprint` in
   `ColorComposerCore/Tests/ColorComposerCoreTests/Support/ParityCorpus.swift`.
   The fingerprint is a 64-bit FNV-1a hash of the file bytes with CRLF line
   endings normalized to LF:

   ```bash
   python3 - <<'PY'
   data = open('ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json','rb').read()
   h = 0xcbf29ce484222325
   for b in data.replace(b'\r\n', b'\n'):
       h ^= b
       h = (h * 0x100000001b3) & 0xFFFFFFFFFFFFFFFF
   print(format(h, '016x'))
   PY
   ```

3. If the upstream corpus gained or dropped scenarios, update the expected
   scenario id set in `testCorpusCoversTiesExclusionsAndWeightHandling`.

4. Run the tests:

   ```bash
   cd ColorComposerCore && swift test --filter SolverParityCorpusTests
   ```

The upstream corpus bumps `algorithm_version` whenever the solver's scoring
semantics change; a version bump means the expectations in the corpus moved
and the mirrored scorer has to follow.

## Note for the implementation phase

The corpus is committed inside the test target directory, so SwiftPM reports
it as an unhandled file until the test target declares it:

```swift
.testTarget(
    name: "ColorComposerCoreTests",
    dependencies: ["ColorComposerCore"],
    path: "Tests/ColorComposerCoreTests",
    resources: [.copy("Fixtures")]
)
```

The test locates the corpus by path (see `Support/TestFixtureLocator.swift`),
so it works with or without that declaration.
