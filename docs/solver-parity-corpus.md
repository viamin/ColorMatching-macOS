# Solver parity corpus

This document records how the macOS app consumes the solver **parity
corpus** published by the Elixir [`color_matching`](https://github.com/viamin/color_matching)
service, so the client's `WeightedSquaredErrorScorer` and the server's
`ColorMatching.WeightedSquaredError` solver can never silently diverge.

## Where the corpus lives

| Copy | Path |
| --- | --- |
| Source of truth (server repo, generated) | `priv/parity/v1/corpus.json` in viamin/color_matching |
| Committed replay fixture (this repo) | `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json` |

The fixture is a **byte-identical copy** of the upstream file (upstream CI
keeps it honest with `mix parity.generate --check`; the generator is fully
deterministic). Never hand-edit the fixture — refresh it wholesale (below).

## What it contains

A stamped contract plus scenarios:

- `algorithm_version: 1` — bump semantics guard. If upstream bumps it, every
  expectation in the corpus has moved; refresh the fixture and treat scorer
  changes deliberately, not as noise.
- `scorer: ColorMatching.WeightedSquaredError`, `selection:
  earliest-index-wins`, `missing_policy:
  excluded-when-any-positive-weight-channel-missing` — the three coupled
  semantics this app mirrors.
- 12 scenarios spanning: strictly distinct errors; exact ties (symmetric
  offsets, duplicate vectors, three-way, zero-weight-channel, large palette);
  missing-candidate and missing-target exclusions; an all-excluded target
  with **no selection**; an unknown weight key (`ultraviolet`) that must be
  ignored; and an exact-match zero-error case.
- Every brightness/weight value is a dyadic rational, so Swift and Elixir
  compute bit-identical doubles and parity is asserted with **exact**
  equality — no floating-point tolerance.

## How the tests consume it

`SolverParityCorpusTests` (in `ColorComposerCore/Tests/ColorComposerCoreTests`)
loads the fixture relative to the test file and, for every scenario:

1. decodes weights, dropping keys outside `LightingCondition`'s canonical
   set (`white`, `red`, `green`, `blue`, `lps`);
2. builds `PaletteColor` candidates and a `TargetResponseVector`, treating
   absent channel keys as *missing measurements* (never zero brightness);
3. scores every candidate with `WeightedSquaredErrorScorer` and compares
   per-index against the corpus — exact double equality, or `excluded`;
4. re-selects with the earliest-index-wins policy (mirroring
   `IlluminantMatching.best_match/4`) and compares `selected_index`,
   `selected_hex_color`, `error`, `tied_indices`, and `tie_broke`.

This mirrors upstream's own `test/color_matching/parity/corpus_test.exs`, so
both suites fail on the same divergence from either side.

## Refreshing the fixture

```bash
curl -fsSL \
  https://raw.githubusercontent.com/viamin/color_matching/<ref>/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json
```

Use the exact server `<ref>` (tag or commit) the app targets. After
refreshing, run `swift test` in `ColorComposerCore/` — the corpus-metadata
test fails if `algorithm_version` moved without the fixture being refreshed
to match, and the replay tests fail on any semantic drift.
