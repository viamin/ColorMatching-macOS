# Solver parity corpus & OpenAPI contract consumption

This document records where the `color_matching` parity corpus and OpenAPI
document live in this repository, how the tests consume them, and how to
refresh them. It backs issue #39 (Adopt generated OpenAPI client and enforce
solver parity with the parity corpus). A README pointer should land alongside
the implementation half of #39; this file is the authoritative reference.

## Solver parity corpus

`WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` solver, and `CompositionSolver`'s
selection mirrors `IlluminantMatching.best_match/4` (lowest weighted squared
error wins, earliest palette index breaks ties). Parity with the Elixir
implementation is enforced by running a committed corpus through the real
solver.

### Where the corpus lives

```
ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/Parity/
├── weighted_squared_error_corpus.json        # upstream corpus (viamin/color_matching#111)
└── weighted_squared_error_corpus.seed.json   # in-repo seed, hand-computed
```

- **Upstream corpus** — generated by the Elixir service
  (viamin/color_matching#111). Until it is committed,
  `SolverParityCorpusTests.testUpstreamParityCorpusIsCommitted` fails; the
  issue is not considered done while that is red.
- **Seed corpus** — cases computed by hand from the documented Elixir
  semantics (the `WeightedSquaredError` doctest, tie policy, exclusion
  policy, weight handling, absence-vs-zero). It is the executable format
  reference and pins the parity rules independent of upstream availability.
  Do not shrink it.

### Format contract

The seed file is the canonical example; the Codable structs at the bottom of
`SolverParityCorpusTests.swift` are the executable schema:

```json
{
  "version": 1,
  "generator": {
    "module": "ColorMatching.WeightedSquaredError",
    "source": "...", "commit": "..."
  },
  "cases": [
    {
      "id": "case-id",
      "description": "…",
      "weights":  { "white": 0.5, "red": 1.0, "green": 1.0, "blue": 0.0, "lps": 1.5 },
      "target":   { "white": 0.8, "red": 0.2, "lps": 0.5 },
      "palette":  [ { "id": 10, "responses": { "white": 0.5, "red": 0.1 } } ],
      "expected": { "selected_id": 10, "score": 0.205, "tie": false, "excluded_ids": [] }
    }
  ]
}
```

Rules the harness enforces:

- Light-source keys are exactly the server vocabulary: `white`, `red`,
  `green`, `blue`, `lps`. Unknown keys fail the case (they are generator
  bugs, not data to drop silently).
- `weights` with value `0` mean the channel is ignored — it is not required
  of candidates. Weights `> 0` are required: a candidate missing any of them
  is excluded and must be listed in `excluded_ids`.
- `expected.selected_id: null` means every candidate is excluded: nothing is
  selectable.
- `expected.tie: true` asserts at least two candidates attain the best score
  and the earliest palette index wins; `false` asserts a unique winner.
- `score` is the weighted squared error of the selected candidate, compared
  with `1e-9` accuracy.
- Visual color does not affect selection; the harness synthesizes a
  deterministic sRGB value from the candidate id.

### How the tests consume it

`SolverParityCorpusTests` auto-discovers **every** `*.json` corpus under
`Fixtures/Parity/` and executes each case as a real 1×1-cell
`CompositionSolver.solve` (one constant brightness grid per active channel),
so scoring, exclusion, and earliest-index tie-breaking all run through
production code. Corpus-level checks require each corpus to declare
`generator.module == "ColorMatching.WeightedSquaredError"` and to contain at
least one tie case and one exclusion case.

### Refreshing the corpus

1. Generate the corpus in the `color_matching` repository (the task added by
   viamin/color_matching#111) and copy the emitted
   `weighted_squared_error_corpus.json` over the file in `Fixtures/Parity/`.
2. Commit both the corpus and the generator commit hash recorded in
   `generator.commit` so any parity failure can be traced to the exact
   Elixir revision.
3. Run `swift test` (or `bin/lint`). A corpus that drops tie or exclusion
   coverage, renames a light source, or changes the format fails loudly.

The seed corpus is never refreshed from upstream — it exists precisely to
catch a corpus (or harness) that quietly narrows what parity means.

## OpenAPI document

The JSON form of the published spec (viamin/color_matching#110) is committed
at `ColorComposerCore/openapi.json` — the same document
`swift-openapi-generator` runs against when regenerating the typed client
used by `PaletteAPIClient`. `OpenAPIContractTests` verifies the document is
committed and that it still exposes the endpoints this app consumes (`GET`
`printer_profiles` and `printer_profile_id`-scoped `GET` `colors`), so spec
drift is caught at test time. To refresh: export the spec from the server
repo as JSON, replace the file, regenerate the client, and run `swift test`.
