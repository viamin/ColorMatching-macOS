# Solver parity corpus

`WeightedSquaredErrorScorer` deliberately mirrors the Elixir
`ColorMatching.WeightedSquaredError` / `IlluminantMatching.best_match/4`
implementation in [`color_matching`](https://github.com/viamin/color_matching).
The parity corpus pins that mirror with executable evidence: the same inputs
(palette, target vector, channel weights) must produce the same selection in
Swift as the Elixir reference does — exactly, including tie cases, exclusions,
and weight handling.

## Where the corpus lives

The canonical copy consumed by tests is committed at:

```
ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/solver_parity_corpus.json
```

The loader (`SolverParityCorpusTests.swift`) resolves the corpus in this order:

1. `$SOLVER_PARITY_CORPUS` — explicit file path override (used when validating
   a freshly exported corpus before committing it)
2. the committed fixture above
3. `color_matching/priv/solver_parity_corpus.json` — a sibling checkout of the
   server repo, if present

If none is found the parity tests **fail** (they never silently skip): parity
without a corpus is unverifiable.

## Corpus schema (version 1)

```json
{
  "version": 1,
  "scorer": "weighted_squared_error",
  "cases": [
    {
      "name": "tie_resolves_to_earliest_palette_entry",
      "weights": { "white": 0.5, "red": 1.0 },
      "palette": [
        { "id": 201, "hex": "#1a0d0d", "responses": { "red": 0.4, "green": 0.6 } }
      ],
      "targets": [ { "red": 0.5, "green": 0.5 } ],
      "expected": [
        { "selected_id": 201, "score": 0.02, "tie": true, "excluded_ids": [301] }
      ]
    }
  ]
}
```

- `weights` — per-channel weights keyed by light source
  (`white|red|green|blue|lps`); a missing key means weight `0` (channel
  inactive — it never triggers exclusion).
- `palette[].responses` — normalized `0...1` brightness keyed by light source;
  a missing key means **unmeasured** (never zero brightness).
- `targets[]` — one entry per target vector; a missing key means the target has
  no value for that condition (which must exclude every candidate when that
  condition is required).
- `expected[]` — one entry per target, in the same order:
  - `selected_id` — palette color id that must be selected; `null` asserts that
    no selection exists.
  - `score` — winning weighted squared error (compared with `1e-9` tolerance).
  - `tie` — when `true`, asserts the winning score is achieved by more than one
    candidate and the **earliest palette entry wins** (the
    `best_match/4` policy).
  - `excluded_ids` — palette color ids that must be unrankable (missing a
    measurement for a weight-`> 0` channel).

The currently committed fixture is a **seed corpus**: its cases are hand-derived
from the Elixir `WeightedSquaredError` doctest (the documented `0.205` example)
and the documented selection semantics. The corpus integrity test additionally
requires the file to cover at least one tie case, one candidate-exclusion case,
and one no-selection case, so a bad refresh cannot silently weaken coverage.

## How the tests consume it

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`:

- `testCorpusIsPresentWellFormedAndCoversRequiredBehavior` — schema version,
  known light-source keys, normalized values, target/expected pairing, and the
  minimum coverage requirements above.
- `testSelectionsMatchCorpusExactly` — for every case and target, runs the
  **real `CompositionSolver`** over 1×1 source grids (so the shipped
  eligibility pre-filter, fast-path scoring, and earliest-wins tie-breaking are
  what gets verified) and asserts the selected palette id, winning score, tie
  outcome, and per-candidate exclusion parity. Targets that lack a required
  channel are asserted at scorer level (no candidate may rank).
- `testExcludedCandidateCountMatchesCorpus` — the solver's
  `excludedCandidateCount` diagnostic must agree with `excluded_ids`.

Run them with:

```bash
cd ColorComposerCore && swift test --filter SolverParityCorpusTests
```

## Refreshing the corpus

The corpus is generated by the `color_matching` server (viamin/color_matching#111):

1. Run the corpus generator in a `color_matching` checkout:
   `mix parity_corpus` (or the task name published with #111) and copy the
   emitted `solver_parity_corpus.json`.
2. Validate it against the Swift consumer before committing:
   ```bash
   cd ColorComposerCore
   SOLVER_PARITY_CORPUS=/path/to/solver_parity_corpus.json swift test --filter SolverParityCorpusTests
   ```
3. Replace the committed fixture at
   `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/solver_parity_corpus.json`
   (keep `version` in sync with what the loader supports) and commit it with a
   message referencing the upstream revision it was generated from.

Every parity failure is a real cross-implementation divergence (or a corpus
stale relative to the server): fix forward — never adjust the corpus to match
the Swift output, and never change scorer semantics to force a pass.
