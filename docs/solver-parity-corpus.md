# Solver parity corpus

`ColorComposerCore` mirrors the Elixir `ColorMatching.WeightedSquaredError`
solver and the earliest-wins selection of `ColorMatching.IlluminantMatching`.
Parity is enforced by replaying the server-generated golden-vector corpus
against `WeightedSquaredErrorScorer` and `CompositionSolver`
(`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`).

## Where the corpus lives

* **Upstream (source of truth):** [`viamin/color_matching`](https://github.com/viamin/color_matching)
  at `priv/parity/v1/corpus.json` — generated by `mix parity.generate`
  (viamin/color_matching#111). Generation is deterministic; upstream CI
  verifies the committed bytes with `mix parity.generate --check`.
* **This repo (committed fixture):**
  `ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json`
  — a byte-identical copy, so `swift test` replays parity with no network
  access.

Corpus v1 contains 12 scenarios covering: distinct errors, symmetric /
duplicate / three-way ties, missing-candidate and missing-target exclusions,
zero-weight channels, all-excluded palettes, single-channel weights, exact
zero-error matches, unknown light-source keys in the weights map, and a mixed
8-candidate palette. Every expectation (per-candidate score, selection,
winning error, tie evidence) is an exact binary fraction, so parity assertions
are exact.

## How to refresh

```bash
curl -fsSL \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/ColorComposerCoreTests/Fixtures/parity/v1/corpus.json
```

or, from a local `color_matching` checkout: `mix parity.generate`, then copy
`priv/parity/v1/corpus.json` over the fixture.

After refreshing, `cd ColorComposerCore && swift test` must stay green. If the
corpus's `algorithm_version` changes, solver semantics moved upstream: every
expectation changed with it — re-baseline deliberately in the same change and
note it in the PR. The parity test guards this: it fails on any mismatch of
`algorithm_version`, `scorer`, `selection`, or `missing_policy`.

## Parity findings (v1 corpus, 2026-11)

* `WeightedSquaredErrorScorer` reproduces **all 12 scenarios exactly**:
  per-candidate scores, exclusions, selections, tie sets, and winning errors
  (verified against a term-by-term reimplementation of the Swift scorer; run
  `swift test` for the executable check).
* **Ties:** the corpus pins earliest-index-wins in three scenarios
  (`tie-symmetric-around-target`, `tie-duplicate-vectors`,
  `tie-three-way-on-lps`). The Swift scorer and the solver fast path
  (`sum < bestError`) both keep the earliest candidate.
* **Exclusions:** missing measurements on any positive-weight channel exclude
  a candidate (`missing-candidate-excluded`) — and a missing target channel
  excludes every candidate (`missing-target-excluded`, asserted at scorer
  level: a `BrightnessGrid` cannot express an absent channel). Zero-weight
  channels neither exclude nor contribute (`zero-weight-channel-missing`).
* **Weight handling:** unknown light-source keys in the weights map
  (`ultraviolet`) are ignored, matching the server's `filter_weights/1` and
  the fixed canonical fields of `ChannelWeights`
  (`unknown-weight-ignored`).

## OpenAPI document (issue #39)

The server publishes an OpenAPI 3 spec at `GET /api/v1/openapi.json`
(unauthenticated; viamin/color_matching#110). The migration to the generated
client vendors that document in `ColorComposerCore` and generates the typed
client with `apple/swift-openapi-generator`; the build wiring is pinned by
`OpenAPIGeneratedClientTests`, and the preserved runtime behavior of
`PaletteAPIClient` by `PaletteAPIClientMigrationContractTests`.

`/api/v1` shape findings for the PR description:

* The two consumed endpoints are unchanged:
  `GET /api/v1/printer_profiles` (`PrinterProfilesResponse`) and
  `GET /api/v1/colors?printer_profile_id=N` (`ColorsResponse`). The schemas
  match the existing DTOs (`id`, `printer_make_model`, `paper_type`,
  `ink_type`; `name`, `hex`, `rgb{r,g,b}`, `palette_id`, `palette_name`,
  `sort_order`, `responses` map).
* Newly documented endpoints the app does **not** consume: a profile-scoped
  `GET /api/v1/printer_profiles/:printer_profile_id/colors`, metamer pairs,
  palettes, and test-sheet/capture flows — out of scope per the issue's
  non-goals.
