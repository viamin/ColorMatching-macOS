# Solver parity corpus

`WeightedSquaredErrorScorer` (and `CompositionSolver`'s earliest-index-wins
selection) deliberately mirrors the Elixir `ColorMatching.WeightedSquaredError`
solver so the macOS app and the `color_matching` server agree on color
selection. Parity is enforced by replaying a golden-vector corpus generated by
the server (issue #39; corpus generator: viamin/color_matching#111).

## Where the corpus lives

* **Upstream (source of truth):** `priv/parity/v1/corpus.json` in
  [viamin/color_matching](https://github.com/viamin/color_matching), generated
  by `mix parity.generate`. Regeneration upstream is deterministic
  (byte-identical) and verified in that repo's CI.
* **This repo (committed copy):**
  `ColorComposerCore/Tests/Fixtures/parity/v1/corpus.json` — a verbatim copy.
  The corpus carries an `algorithm_version` stamp (currently `1`); the parity
  test pins it and fails loudly if a refreshed corpus bumps the version, so a
  solver-semantics change is never silently absorbed.

## How the tests consume it

`ColorComposerCore/Tests/ColorComposerCoreTests/SolverParityCorpusTests.swift`
loads the fixture and asserts, for every scenario:

1. **Scores** — each palette candidate's `WeightedSquaredErrorScorer` score
   matches the corpus exactly (the corpus values are exact dyadic rationals,
   so exact `Double` equality is meaningful), including `"excluded"` outcomes.
2. **Selection** — `CompositionSolver.solve` on a 1×1 target grid reproduces
   the expected `selected_index`, `error`, and selected hex color, including
   the all-excluded/no-selection scenarios.
3. **Ties** — indices tied at the minimum score and the `tie_broke` flag match
   the corpus tie evidence (earliest index wins).
4. **Edge semantics** — missing-measurement exclusion on any positive-weight
   channel, zero-weight channels being ignored (missing or divergent values on
   them neither exclude nor contribute), and unknown weight keys (e.g.
   `ultraviolet`) being dropped.

A target missing a positively-weighted channel cannot be expressed through
`solve` (the app models that as a missing source image); the test asserts the
scorer excludes every candidate in that case and that `solve` throws
`missingSourceGrid`.

## Refreshing the corpus

When the upstream corpus changes (e.g. `algorithm_version` bumps or new
scenarios are added):

```sh
curl -fsSL \
  https://raw.githubusercontent.com/viamin/color_matching/main/priv/parity/v1/corpus.json \
  -o ColorComposerCore/Tests/Fixtures/parity/v1/corpus.json
```

Then check `algorithm_version`: if it is no longer `1`, update the pinned
metadata assertions in `SolverParityCorpusTests` as part of the same change —
a version bump means solver semantics changed upstream and parity of this
app's scorer must be re-evaluated, not just re-recorded. Finally run
`swift test` (from `ColorComposerCore/`).

## Parity findings (v1 corpus, algorithm_version 1)

* **Ties:** earliest-index-wins selection is confirmed on four deliberate tie
  scenarios (symmetric-around-target, duplicate vectors, three-way tie on a
  single channel, and a mixed eight-color palette with a tied best trio).
* **Exclusions:** a candidate missing any positive-weight channel is excluded
  rather than treated as zero brightness; when every candidate is excluded
  there is no selection (`colorIndices` nil, error `+∞`).
* **Weight handling:** weights scale squared error per channel; zero-weight
  channels neither exclude nor contribute; non-canonical weight keys are
  ignored.

## Related: generated OpenAPI client

Issue #39 also migrates `PaletteAPIClient` to a typed client generated from
the server's OpenAPI document (viamin/color_matching#110, served at
`GET /api/v1/openapi.json`). Two test files cover that migration:

* `PaletteAPIClientContractTests` pins the wire behavior that must survive the
  migration (paths, query, headers, snake_case decoding, error mapping).
* `GeneratedClientAdoptionTests` guards that the OpenAPI document and the
  `swift-openapi-generator`/`swift-openapi-runtime` dependencies stay vendored.
