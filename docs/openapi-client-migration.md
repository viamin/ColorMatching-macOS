# OpenAPI generated-client migration notes (issue #39)

Working notes for migrating `PaletteAPIClient` to a typed client generated by
`swift-openapi-generator` from the server's published OpenAPI 3 spec, plus the
`/api/v1` shape findings recorded for the PR description. The code changes
(Package.swift dependencies, plugin, `openapi.yaml`, generated sources) belong
to the implementation phase; this phase commits the tests that pin the contract.

## Spec source

- The server (viamin/color_matching#113) serves the spec dynamically at
  `GET /api/v1/openapi.json` — it is not committed as a static artifact upstream.
- To generate: fetch the document from a running server (or render it from the
  `ColorMatchingWeb.ApiSchemas` modules), save it as
  `ColorComposerCore/OpenAPI/color-matching.yaml|json`, and wire the
  `OpenAPIGenerator` build tool plugin per apple/swift-openapi-generator docs.
- Keep `PaletteAPIClient`'s public surface (or wrap the generated client behind
  it) so `ColorMatching` app code and the disk-cache/offline-stale behavior in
  `ProfileColorCache` are untouched.

## `/api/v1` shape findings (spec vs current DTOs)

Comparing the published schemas with `APIModels.swift`:

- Envelopes are unchanged: `{"printer_profiles": [...]}` and
  `{"printer_profile": ..., "colors": [...]}` with snake_case keys — the current
  `.convertFromSnakeCase` decoding matches.
- **Tightened requiredness:** the spec marks `name`, `palette_id`, and
  `sort_order` as **required** on each color, and `printer_make_model`,
  `paper_type`, `ink_type` as required on each printer profile. The current DTOs
  model all of these as optionals (legacy tolerance). A generated client will
  surface them as non-optional; the wrapper should keep tolerating older
  servers or the migration should note the version floor.
- `palette_name` is explicitly `nullable: true` — keep it optional.
- `responses` is an open `additionalProperties` object; unknown light-source
  keys must stay ignorable (see `PaletteColorDTO.toDomain()`).
- No endpoint/path changes for the surfaces this app consumes
  (`GET /api/v1/printer_profiles`, `GET /api/v1/colors?printer_profile_id=N`).

## Behavior pinned by tests (must stay green post-migration)

`PaletteAPIWireContractTests` holds the migration to the observable contract:

- request paths `/api/v1/printer_profiles` and `/api/v1/colors` with the
  `printer_profile_id` query parameter;
- `Accept: application/json` and trimmed `Authorization: Bearer …` headers;
- HTTP 401 → `PaletteAPIError.unauthorized` (distinct from other non-2xx →
  `.badStatus`, and undecodable bodies → `.malformedResponse`);
- decoding of spec-shaped envelopes, including colors whose every
  OpenAPI-required field is present, nullable `palette_name`, response
  provenance fields, measured-zero vs. missing measurements, and response-less
  colors;
- `testConnection()` semantics (succeeds on any 2xx, throws `.unauthorized` on 401);
- domain conversion of fetched colors for the solver.

Disk-cache/offline behavior is covered separately by
`ProfileColorCacheTests` (per-server/profile storage, stale reads) and must not
change: the client swap is transport-level only.
